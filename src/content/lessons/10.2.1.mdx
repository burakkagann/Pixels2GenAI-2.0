## Big Question — *what does a Python pipeline look like when redrawn as a node graph?* <a id="big-question"></a>

The cleanest way to internalise TouchDesigner's paradigm is to take a concept you already know in Python and *port it node-by-node*. Three exercises from Modules 1-3 are well-suited because they exercise the three operations every real-time pipeline performs: **generation** (build a signal from nothing), **transformation** (modify a signal), and **filtering** (extract structure from a signal). After this lesson the translation between NumPy and TD operators stops feeling like a foreign language and starts feeling like a dialect of the same language.

### Learning objectives

<ol class="obj-list">
  <li>Translate a NumPy gradient generator into a Ramp TOP + Level TOP chain.</li>
  <li>Translate an affine transform (rotate + scale + translate) into a Transform TOP with parameter exports from CHOPs.</li>
  <li>Translate a Sobel edge detector into a Convolve TOP with the matching kernel.</li>
  <li>Recognise the four NumPy → TD translation rules: array → TOP, operation → operator, variable → wire, time loop → continuous cooking.</li>
</ol>

## Part 1 — Generation: from `np.linspace` to Ramp TOP <a id="part-1"></a>

In Module 2 we generated colour gradients in Python with `np.linspace` and array broadcasting:

<CodeBlock lang="python" file="gradient_python.py">
```python
W, H = 1024, 1024
xs = np.linspace(0, 1, W)
ys = np.linspace(0, 1, H)[:, None]
gradient = np.stack([xs * np.ones((H, W)),
                     ys * np.ones((H, W)),
                     0.4 * np.ones((H, W))], axis=-1)
Image.fromarray((gradient * 255).astype(np.uint8)).save('gradient.png')
```
</CodeBlock>

The same output in TouchDesigner is one operator: a **Ramp TOP** with type set to `Linear`, `Horizontal Linear`, or `Radial`. Parameters control direction, gradient stops, and colour interpolation. To layer two ramps (horizontal red + vertical green), use two Ramp TOPs feeding a Composite TOP set to `Add`. The whole pipeline:

```
Ramp TOP (horizontal red)   ╲
                             ┝→ Composite TOP (Add) → Null TOP
Ramp TOP (vertical green)   ╱
```

**Translation rule 1**: every NumPy *generation* operation has a "factory" TOP that produces the same data: `Ramp` for gradients, `Noise` for noise, `Circle/Rectangle/Text` for shapes.

<Admonition type="dyk" title="Did you know? · Ramp TOP genealogy">
The Ramp TOP descends directly from the *Ramp SOP* in Houdini, where it was introduced in the 1990s to colour particles by their age. Houdini and TouchDesigner share an operator-family ancestry — both are products of Side Effects' dataflow philosophy — and the operator names are often identical [1].
</Admonition>

## Part 2 — Transformation: from matrix math to Transform TOP <a id="part-2"></a>

Module 3 covered affine transformations. The Python version of rotating an image by `theta` radians around its centre and scaling by `s` is a sequence of matrix operations on pixel coordinates:

<CodeBlock lang="python" file="transform_python.py">
```python
from PIL import Image
img = Image.open('input.png')
out = img.rotate(np.degrees(theta), resample=Image.BICUBIC)
out = out.resize((int(w * s), int(h * s)))
out.save('output.png')
```
</CodeBlock>

In TouchDesigner this is one operator — **Transform TOP** — with parameters `Rotate`, `Scale`, `Translate`. Wire your source image into its input, set the parameters, and the output cooks every frame:

```
Movie File In TOP → Transform TOP (rotate, scale, translate) → Null TOP
```

The interesting move is *animating* the parameters. Drag an LFO CHOP onto the Transform TOP's `rotate` parameter and choose "Export Parameter." Now the LFO drives the rotation continuously. Add another LFO at a different frequency on `scale` and the image breathes and spins simultaneously, without any Python code.

**Translation rule 2**: any *single Python operation* becomes one operator. Multi-step transformations become operator chains. CHOPs animate parameters — that is what they exist for.

<Admonition type="important">
TD has both `Transform TOP` (2D image transform) and `Transform SOP` (3D geometry transform). They are family-specific; the SOP version cannot transform an image, the TOP version cannot transform geometry. The operator-family discipline from 10.1.1 reasserts itself constantly — pick the right family.
</Admonition>

## Part 3 — Filtering: from convolution to Convolve TOP <a id="part-3"></a>

Module 3.4.2 (edge detection) used the Sobel kernel applied via `scipy.signal.convolve2d`:

<CodeBlock lang="python" file="sobel_python.py">
```python
from scipy.signal import convolve2d
sobel_x = np.array([[-1, 0, 1], [-2, 0, 2], [-1, 0, 1]])
sobel_y = sobel_x.T
gx = convolve2d(image, sobel_x, mode='same')
gy = convolve2d(image, sobel_y, mode='same')
magnitude = np.sqrt(gx**2 + gy**2)
```
</CodeBlock>

TouchDesigner has a **Convolve TOP** that takes a kernel matrix as a parameter. The chain:

```
Source TOP → Convert TOP (to grayscale) ╲
                                          ╲→ Convolve TOP (Sobel-X) → Math TOP (squared) ╲
                                          ╱→ Convolve TOP (Sobel-Y) → Math TOP (squared) ╱→ Add TOP → Math TOP (sqrt) → Null
```

The shape mirrors the NumPy version exactly — same kernel, same operations, same output. The difference is that the chain re-cooks every frame, so feeding a live webcam into the source slot gives you live edge detection at 60 fps.

**Translation rule 3**: any NumPy *filter* (convolution, blur, sharpen, edge) has a direct TOP counterpart — `Convolve`, `Blur`, `Edge`, `LumaLevel`. The kernel parameter format is identical to the NumPy matrix.

**Translation rule 4**: a Python `for t in range(num_frames):` loop becomes *the absence of a loop*. The network already runs every frame; you do not write the loop.

## Synthesis project — port three Module 1-3 exercises <a id="synthesis"></a>

Pick three exercises from Modules 1-3 you understand well in Python. Rebuild each as a TD network. Document the operator chain. Note which Python lines correspond to which operators. The mapping table emerges naturally.

| Python operation                  | TD operator         |
| --------------------------------- | ------------------- |
| `np.linspace`, `np.linspace * ones` | Ramp TOP            |
| `np.random.rand`, `np.random.normal` | Noise TOP           |
| Array `+`, `-`, `*`, `/`          | Math TOP, Composite TOP |
| `gaussian_filter`                 | Blur TOP            |
| `convolve2d` with custom kernel   | Convolve TOP        |
| `np.dstack`, `np.stack`           | Composite TOP, Reorder TOP |
| `.rotate()`, `.resize()`          | Transform TOP       |
| `time.sleep` / frame counter      | Continuous cooking (no analog) |

**Reflection questions**

- Why does the time loop disappear in the TD version?
- The Python version uses `mode='same'` to handle edges. What does the TD Convolve TOP do for edges?
- You want to apply a 64×64 custom kernel. Would you use Convolve TOP or write a GLSL TOP shader? Why?

<Dropdown summary="Answers">

**The disappearing loop** — every TD operator already cooks every frame. The Python `for t in range(...)` is essentially the network's outer loop, externalised by the framework. You write the *body* of the loop (the operator chain) and the framework iterates it.

**Edges** — Convolve TOP has an `Edge Mode` parameter: zero, repeat, mirror, clamp. Different choices produce different artefacts at the image border, identical to scipy's `mode` parameter for `convolve2d`.

**64×64 kernel** — Convolve TOP supports arbitrary kernel sizes but cost grows as kernel area. A 64×64 kernel costs 4096 multiply-adds per pixel and at 1080p that is 8 billion ops per frame. For anything beyond about 7×7 kernels, write a GLSL TOP fragment shader; the GPU can absorb the cost where Convolve TOP cannot.

</Dropdown>

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

Three core Python pipelines port one-to-one onto TouchDesigner networks. Generation becomes Ramp/Noise/Shape TOPs. Transformation becomes Transform TOP with CHOP-exported parameters. Filtering becomes Convolve/Blur/Edge TOPs. The time loop disappears — TD's continuous cooking *is* the loop. Once you have ported three or four Python exercises, the translation rules stop feeling like translation and start feeling like writing in the same language with different punctuation.

</Admonition>

**Common pitfalls to avoid**

- Trying to translate Python control flow (if/while/for) into TD operators. Use a Script DAT for control logic instead.
- Forgetting `Convert TOP` between RGB and grayscale stages. Convolution operators often want single-channel input.
- Using Composite TOP `Over` mode when you wanted `Add`. Read the Composite mode parameter every time.
- Writing the time variable as a constant. Use `absTime.seconds` in parameter expressions, not a fixed numerical value.
- Re-implementing edge detection with a Script TOP for "control." The native Convolve TOP is dramatically faster.
