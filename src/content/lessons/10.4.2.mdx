## Big Question — *how do you let a MIDI controller drive 50 visual parameters without writing 50 separate connections?* <a id="big-question"></a>

By the time you reach a polished interactive project, you have a control surface (knobs, sliders, buttons, external MIDI, OSC from a phone app, audio reactivity, motion-tracker data) and a visual network with many tweakable parameters. The naive way to connect them is one-by-one: this knob → this parameter, that slider → that parameter. Past about ten connections this becomes unmanageable: parameter names change, mappings need scaling and curves, the same input might need to drive two parameters with different curves. The professional pattern is a **mapping layer**: a separate sub-network that takes raw controller input, normalises it, applies curves and scaling, and produces clean, named control channels that your visuals consume. The visuals never know what kind of controller is driving them, and the controllers never know what visual parameters exist. The mapping layer in the middle is what makes both halves swappable.

### Learning objectives

<ol class="obj-list">
  <li>Decompose any controller-to-visual connection into four steps: receive, normalise, curve, drive.</li>
  <li>Use MIDI In CHOP, OSC In CHOP, and Audio Spectrum CHOP as the standard receive operators.</li>
  <li>Apply Math CHOP and Lookup CHOP for normalisation and curve shaping.</li>
  <li>Design a mapping layer that decouples controllers from visual parameters via named intermediate channels.</li>
</ol>

## Part 1 — The four-step pipeline <a id="part-1"></a>

Every controller-to-parameter mapping has the same shape:

1. **Receive** the raw input (MIDI note, OSC value, audio sample, mouse position) using the appropriate input CHOP.
2. **Normalise** the value to a known range (typically `[0, 1]`).
3. **Curve** the value through a non-linear shape (exponential for brightness, logarithmic for volume, S-curve for threshold gates).
4. **Drive** a visual parameter by referencing the curved channel from a parameter expression.

Each step is one operator. The whole chain for "MIDI knob 1 → blur amount, with a gentle S-curve" is four operators:

```
MIDI In CHOP → Math CHOP (normalise) → Lookup CHOP (S-curve) → (consumed by Blur TOP)
```

The downstream visual operator references the final channel via `op('path/to/output')['mapped_value']`. There is no other connection between controller and visual.

<Admonition type="dyk" title="Did you know? · MIDI's 7-bit legacy">
MIDI 1.0, designed in 1983, transmits values as 7-bit integers in `[0, 127]`. The normalisation step is therefore always `value / 127.0`. MIDI 2.0 (released 2020) supports 16-bit and 32-bit values; if you target only MIDI 2.0 controllers your normalisation changes. Most live-performance MIDI is still 1.0, so the divide-by-127 step is the standard everywhere [1].
</Admonition>

## Part 2 — The standard receive operators <a id="part-2"></a>

**MIDI In CHOP** — connects to any MIDI device. Produces one channel per CC message, with values `[0, 127]`. Configure the device, channel, and channel-number range; the CHOP outputs the live values.

**OSC In CHOP** — listens on a UDP port for OSC messages (the protocol used by TouchOSC, Lemur, and most modern controller apps). Configure the port; the CHOP outputs one channel per OSC address.

**Audio Spectrum CHOP** — takes an Audio In CHOP and produces a per-frequency-band amplitude curve. Pick the band you care about (bass, mids, treble) and you have an audio-reactive control signal.

**Mouse In CHOP** — outputs the cursor's `x`, `y` (in the active panel) and button states. The simplest controller, always available.

**Keyboard In CHOP** — outputs key-down booleans for arbitrary keys.

Each of these CHOPs has different units and ranges. Normalisation in the next step brings them all into `[0, 1]`.

## Part 3 — Normalisation, curves, and the named-channel discipline <a id="part-3"></a>

**Normalisation** is one Math CHOP per input source. Set the `from range` (e.g. `0..127` for MIDI) and `to range` (`0..1`). The output is unit-normalised; downstream steps assume `[0, 1]` input.

**Curves** are applied with Lookup CHOP. It takes an input channel (`[0, 1]`) and looks up a curve table to produce a non-linear output. Common curves:

- **Linear** — passes through unchanged. Pointless except as a placeholder.
- **Exponential** (`x^2`, `x^3`) — slow-start, fast-end. Good for brightness controls where small values should feel like "nothing yet."
- **Logarithmic** (`log(1+x)`) — fast-start, slow-end. Good for volume controls (matches perceptual loudness).
- **S-curve** (sigmoid, smoothstep) — slow-start, fast-middle, slow-end. Natural-feeling for blends and crossfades.
- **Threshold** (step function) — flat-then-jump. For trigger-style mappings where a knob beyond 50% turns something on.

**Named channels** — give every normalised+curved channel a meaningful name (`bass_amp`, `slider_brightness`, `knob_blur`). Downstream visual operators reference channels by these names, not by raw MIDI/OSC paths. If you swap a MIDI controller for an OSC tablet, you change only the receive layer; the named channels still exist with the same names, and the visual layer keeps working.

<Admonition type="important">
The named-channel discipline is *the entire point* of the mapping layer. Without it, you have point-to-point connections that break when the input source changes. With it, the controller layer and the visual layer are independent and either can be replaced without touching the other.
</Admonition>

## Synthesis project — a clean MIDI-to-Visual pipeline <a id="synthesis"></a>

Build a Base COMP called `input_layer` that:

1. Takes a MIDI controller's 8 knobs as input.
2. Normalises each to `[0, 1]`.
3. Applies a per-knob curve (knob 1 exponential for brightness, knob 2 linear, knob 3 logarithmic for volume...).
4. Outputs 8 named channels: `knob_brightness`, `knob_volume`, etc.

The downstream visual network references the named channels by `op('/input_layer/output')['knob_brightness']`. Now swap the MIDI controller for an OSC In CHOP without touching anything else — the visual network keeps working because the named channels still exist.

**Reflection questions**

- A MIDI knob value of 64 (the centre) maps to `0.50` after linear normalisation. Why might you want it to map to `0.50` *exactly* after curve application as well?
- Audio amplitude is naturally logarithmic in perception. What's the right curve to apply to an Audio In CHOP's raw amplitude before driving a brightness parameter?
- Your MIDI controller's knob 1 jitters slightly — values oscillate ±2 around the steady value. What CHOP fixes this?

<Dropdown summary="Answers">

**Centre = 0.50** — many curves break this property: `x²` maps 0.50 to 0.25. If your knob has a centre detent or visual "centre marker", you want the curve to be *centred at 0.5*: `x → 0.5 + 0.5*sign(x-0.5)*|2(x-0.5)|^γ` keeps the centre fixed while applying gamma curvature elsewhere. Test centre alignment explicitly when designing curves.

**Audio brightness curve** — log-scale the audio, then linear-map to brightness. `np.log10(1 + raw_amp * 9)` maps `[0, 1]` to `[0, 1]` but emphasises low values (matching perceptual loudness). For a brightness mapping that "feels right", logarithmic on the input + linear curve from Lookup CHOP works well.

**Jittery knob** — a Filter CHOP with a small `Filter Width` (e.g. 0.2s exponential filter) smooths the signal. The cost is a small lag — usually acceptable for slow human movement, occasionally not for fast trigger gestures.

</Dropdown>

#### Make it your own

- **Multi-source mapping**: combine MIDI knob 1 + audio bass into one named channel `intensity = max(knob, audio)`. Whichever input is louder drives the visual.
- **Recordable mapping**: a Script DAT that captures the current value of every named channel on a button press, then plays them back as automation. The mapping layer becomes a recording surface.
- **Smoothing per channel**: every output channel goes through a Filter CHOP with a *configurable smoothing time*. Smooth audio mappings; instantaneous MIDI mappings.

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

Controller-to-visual mapping is a four-step pipeline: receive, normalise, curve, drive. MIDI In, OSC In, Audio Spectrum, Mouse In are the standard receive operators. Math CHOP normalises to `[0, 1]`; Lookup CHOP applies non-linear curves. The architectural discipline is to use a **mapping layer** Base COMP that translates between controller-specific inputs and named intermediate channels. Visual operators reference channels by name, never by raw input source. With this in place, you can swap controllers without rewriting visuals.

</Admonition>

**Common pitfalls to avoid**

- Point-to-point connections from MIDI CHOP straight into visual operator parameters. Fine for prototypes, miserable at scale.
- Forgetting to normalise. MIDI's 0-127 range plus a visual operator's "size" parameter that wants 0-50 produces unexpected behaviour.
- Using linear curves everywhere. Most controls feel more natural with exponential or logarithmic curves.
- Filtering everything. Filtering introduces latency; trigger-style controls (buttons, gestures) need unfiltered paths.
- Hard-coding MIDI CC numbers in 30 places. Centralise them in the mapping layer.
