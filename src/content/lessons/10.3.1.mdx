## Big Question — *when should you reach for a Script operator instead of a native one?* <a id="big-question"></a>

A Script TOP can produce any pixel output your NumPy can compute. A Script CHOP can produce any numeric channel array. A Script SOP can produce any 3D geometry. They are TouchDesigner's escape hatches into the rest of the Python ecosystem: bring in OpenCV, scikit-learn, PyTorch, your own NumPy code from Modules 1-7. The catch is performance. Native operators run as compiled C++; Script operators run Python, which is 10–100× slower for per-pixel or per-element work. The skill is recognising the cases where the *expressiveness* of Python outweighs the cost — anomaly-detection logic, ML inference, CSV parsing, arbitrary algorithms with no native equivalent — and the cases where you should hunt for a native operator instead.

### Learning objectives

<ol class="obj-list">
  <li>Identify the three Script operator variants — Script TOP (pixels), Script CHOP (channels), Script SOP (geometry) — and the data each consumes and produces.</li>
  <li>Write the `onCook` callback that produces the operator's output from its inputs.</li>
  <li>Persist state between cooks using module-level globals or `me.storage`.</li>
  <li>Recognise the four signs that you should rewrite a Script operator as a native one (or as a GLSL shader).</li>
</ol>

## Part 1 — The three Script operator variants <a id="part-1"></a>

**Script TOP** — outputs a 2D pixel array. The callback receives `scriptOp` and the operator's inputs (themselves TOPs). You read inputs as NumPy arrays via `op.numpyArray(delayed=False)` and write the output via `scriptOp.copyNumpyArray(arr)`. Use for: ML inference on images, OpenCV pipelines, NumPy/SciPy image algorithms that have no TOP equivalent.

<CodeBlock lang="python" file="script_top.py">
```python
def onCook(scriptOp):
    inp = scriptOp.inputs[0].numpyArray(delayed=False)
    # inp.shape == (H, W, 4) with RGBA channels in [0, 1]
    out = some_numpy_pipeline(inp)
    scriptOp.copyNumpyArray(out.astype(np.float32))
    return
```
</CodeBlock>

**Script CHOP** — outputs 1D channel arrays. The callback creates channels with `scriptOp.appendChan('name')` and fills `.vals` with a list of floats. Use for: custom signal generators, NumPy-driven physics (like the boids physics in 10.2.2), any per-element vector math.

**Script SOP** — outputs 3D geometry: vertices, edges, polygons. The callback builds the geometry programmatically. Use for: procedural mesh generation, CSV-loaded point clouds, L-system trees, any geometry that does not fit Sphere/Box/Torus primitives.

<Admonition type="dyk" title="Did you know? · The escape hatch principle">
"Visual programming for the easy 80%, text programming for the hard 20%" is a design principle older than TouchDesigner. Max/MSP added the `js` and `python` objects in the early 2000s for the same reason. Houdini has VEX scripts inside every node. Even Unreal Blueprints have a "C++ event" escape hatch. Every node-based environment that has lasted long enough to grow up has shipped a text-programming escape hatch [1].
</Admonition>

## Part 2 — The `onCook` callback and state persistence <a id="part-2"></a>

Each Script operator has an `onCook` callback that runs every time the operator cooks (typically once per frame). The callback is *the* entire script. To make state persist between cooks, store it in a module-level global variable or in `me.storage`:

<CodeBlock lang="python" file="state_persist.py">
```python
# Module-level: simplest, scoped to this script
state = {'frame': 0, 'history': []}

def onCook(scriptOp):
    state['frame'] += 1
    state['history'].append(state['frame'])
    # use state['history'] for whatever
    return
```
</CodeBlock>

For long-lived state shared across multiple scripts, use `me.storage`, which is a TD-managed key/value store attached to the operator and survives reloads:

<CodeBlock lang="python" file="storage_demo.py">
```python
def onCook(scriptOp):
    history = me.storage.get('history', [])
    history.append(scriptOp.time.frame)
    me.storage['history'] = history
    return
```
</CodeBlock>

`me.storage` is automatically saved with the project file, so reloading restores the state. Module-level globals reset every time the project loads.

<Admonition type="important">
Do **not** use TouchDesigner DAT cells to persist state from a Script operator. They were not designed for that. Use `me.storage`.
</Admonition>

## Part 3 — When to replace Script with native <a id="part-3"></a>

Four signs your Script operator should be rewritten:

**1. Per-pixel work.** A Script TOP doing per-pixel NumPy is 10–50× slower than the equivalent native TOP chain. Convolution, blur, edge detection, levels, composite — *all* have native TOPs. If your Script TOP can be expressed as a chain of native TOPs, use the chain.

**2. Heavy per-element CHOP work.** Filtering 10,000 channel values per frame in Python takes milliseconds. The native Filter, Math, and Logic CHOPs do it in microseconds.

**3. The operation is in NumPy's broadcast set.** Anything `np.add`, `np.multiply`, `np.where` can do is `Math TOP`, `Composite TOP`, `Logic TOP` faster.

**4. The operation is in OpenGL's fragment-shader set.** Anything per-pixel that does not fit a single TOP is 100× faster as a GLSL TOP (lesson 10.2.4).

Cases where you *should* keep the Script operator:

- ML inference (PyTorch, ONNX Runtime).
- Loading external data (web APIs, custom file formats).
- One-shot setup at project load.
- Complex control logic that the visual editor would obscure.

| Workload                                  | Script op cost | Native cost | Decision |
| ----------------------------------------- | -------------- | ----------- | -------- |
| 1080p Gaussian blur                       | 30 ms          | 0.3 ms      | Native (Blur TOP) |
| 1080p YOLOv8 inference                    | 18 ms (ONNX)   | n/a         | Script TOP (only option) |
| 100,000 CHOP samples filtered             | 4 ms           | 0.05 ms     | Native (Filter CHOP) |
| OpenCV optical flow                       | 12 ms          | n/a         | Script TOP |
| Reaction-diffusion (per-pixel)            | 80 ms          | 1 ms        | GLSL TOP |

<Admonition type="note">
A useful debugging step: replace your Script TOP with a `Pass Through TOP` and confirm the frame budget recovers. If yes, the Script TOP is your bottleneck and you should rewrite it. If no, the bottleneck is elsewhere and you can leave the Script operator alone.
</Admonition>

## Synthesis project — when Python is worth it <a id="synthesis"></a>

Build two versions of the same effect:

1. A Script TOP that takes a webcam input, runs OpenCV's `cv2.Canny` edge detector, and outputs the result.
2. A native TOP chain that approximates the same effect using Convolve TOP with Sobel kernels.

Profile both in the Performance Monitor. Notice that OpenCV's edge detector is *better* (proper hysteresis thresholding) but takes 5-8 ms per frame. The native chain is rougher but takes 0.5 ms. Pick the trade-off that matches your needs.

**Reflection questions**

- Why does a Script TOP doing per-pixel NumPy work cost 10-50× more than the equivalent native TOP?
- Your Script CHOP outputs 10,000 channel values. Memory allocation each frame is suspect — what is the cure?
- A Script operator with no inputs costs 0.1 ms per frame *doing nothing*. What is that floor, and can it be lowered?

<Dropdown summary="Answers">

**Why 10-50× slower** — native TOPs run as compiled C++ with manual memory management and explicit SIMD instructions, on the GPU for many operators. A Script TOP runs CPython, which has interpreter overhead, garbage collection pauses, and Python's data model (every int is an object). NumPy mitigates most of the per-element cost but the boundary cost — passing data in and out of Python — remains.

**10,000 values, allocation each frame** — re-use a pre-allocated NumPy array stored in module-level state or `me.storage`. Allocate once at project load; fill in-place each frame. Saves the `O(N)` allocation cost and lets the JIT predictably reuse memory.

**0.1 ms floor, lowering it** — the floor is the Script operator's *cook overhead* — the interpreter dispatch, callback resolution, and TD-side bookkeeping. You cannot lower it by editing the script; only by removing the script entirely. If you have 50 Script operators doing nothing each, the cumulative 5 ms is significant.

</Dropdown>

#### Make it your own

- **Profile a real ML model**: load a TorchScript module in a Script TOP, run inference per frame on the webcam input. Measure cook time. ResNet50 will be ~50 ms; MobileNet will be ~10 ms; quantised tiny models can fit under 5 ms.
- **Numba-jit your Script CHOP**: import `numba`, jit-compile the inner loop. Often a 10-20× speedup over pure NumPy for non-vectorised code.
- **Replace one Script with a native chain**: pick a Script you have written, rewrite as native operators, measure the difference.

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

Script TOP, Script CHOP, and Script SOP are TouchDesigner's escape hatches into Python and NumPy. They run `onCook` every frame and persist state via module globals or `me.storage`. The cost: 10-50× slower than native operators. Use Script operators for ML inference, external data loading, and one-shot setup. Avoid them for per-pixel image processing (use native TOPs or GLSL), per-element CHOP work (use native CHOPs), or anything expressible as broadcast NumPy (almost always has a native equivalent). The decision matrix is: "is there a native operator that does this?" — if yes, use it; if no, Script is your tool.

</Admonition>

**Common pitfalls to avoid**

- Doing per-pixel work in a Script TOP. The output looks fine; the frame rate plummets.
- Allocating NumPy arrays inside `onCook` instead of pre-allocating.
- Storing state in DAT cells instead of `me.storage`.
- Using a Script CHOP to do what `Math CHOP` and `Filter CHOP` already do natively.
- Importing heavy libraries (PyTorch, OpenCV) at module level if you only need them for a one-shot — import lazily inside a function that runs once.
