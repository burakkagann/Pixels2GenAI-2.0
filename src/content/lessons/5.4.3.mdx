## Overview <a id="overview"></a>

Real botanical trees do not grow according to L-systems' rigid recursion. They grow opportunistically — toward sunlight, toward water, around obstacles. Adam Runions and collaborators captured that in 2007 with the **Space Colonization Algorithm**: scatter "attractors" — points the tree wants to reach — in a 2D area, then grow the tree toward them one segment at a time. Each attractor influences whichever tree node is closest. When the tree node grows close enough to an attractor, the attractor is **consumed** and disappears. The result is a tree that fills the attractor cloud naturally, branches where it must, and stops where it has nowhere to go. The algorithm is now the basis of SpeedTree, Houdini's `tree-grow` SOP, and the foliage tools in every major game engine [1].

### Learning objectives

<ol class="obj-list">
  <li>Represent a tree as a flat array of node positions plus a parent-index for each node.</li>
  <li>Compute "closest node per attractor" with vectorised NumPy pairwise distances.</li>
  <li>Aggregate per-node growth directions as the mean of unit vectors toward influencing attractors.</li>
  <li>Use a consume-on-proximity rule to terminate growth into already-filled regions.</li>
</ol>

## Quick start — one growth iteration <a id="quick-start"></a>

<CodeBlock lang="python" file="quick_start.py">
```python
deltas = attractors[active] - nodes        # broadcasting (n_a, n_n, 2)
dist = np.linalg.norm(deltas, axis=-1)     # (n_a, n_n)
closest = dist.argmin(axis=1)              # which node each attractor pulls

directions = defaultdict(list)
for a_local, (c, d) in enumerate(zip(closest, dist.min(axis=1))):
    if d > INFLUENCE_RADIUS:
        continue
    v = attractors[active[a_local]] - nodes[c]
    directions[c].append(v / np.linalg.norm(v))

for c, dirs in directions.items():
    mean = np.array(dirs).mean(axis=0)
    new_node = nodes[c] + SEGMENT_LENGTH * mean / np.linalg.norm(mean)
    nodes.append(new_node); parents.append(c)
```
</CodeBlock>

The reason this looks "tree-like" — rather than like a uniform fan or a random scatter — is the influence radius. Attractors only pull on nodes within ~70 px, so the tree must physically grow into a region before that region's attractors steer it. This is what produces the natural-looking bifurcations.
</Admonition>

## Core concepts <a id="core-concepts"></a>

### Concept 1 — Tree as flat array + parent indices

The tree is stored as two parallel lists: `nodes` (2D positions) and `parents` (index of the parent node, or `-1` for the root). New nodes append to both lists.

<CodeBlock lang="python" file="tree_demo.py">
```python
nodes = [seed_position]
parents = [-1]
# ...
nodes.append(new_position)
parents.append(parent_node_index)
```
</CodeBlock>

Why flat arrays instead of recursive node objects? Speed and vectorisation. NumPy can compute pairwise distances on `nodes_arr` in one expression. Building a linked-list tree of Python objects would be 50× slower at this scale.

<Admonition type="dyk" title="Did you know? · Same data layout in PBR ray tracing">
Production ray tracers store millions of triangles and BVH nodes as flat arrays with parent/child indices, for exactly the same reason — cache locality and vectorisation. The "flat array plus parent index" pattern is one of the deepest ideas in performance-oriented data structures, and it generalises from graphics to physics to ML.
</Admonition>

### Concept 2 — Closest-node-per-attractor via broadcasting

Each iteration, for every still-active attractor, find the closest tree node. Vectorise the whole thing with one broadcast.

<CodeBlock lang="python" file="closest_demo.py">
```python
deltas = attractors[active_idx][:, None, :] - nodes_arr[None, :, :]
dist = np.linalg.norm(deltas, axis=-1)         # (n_attractors, n_nodes)
closest_node = dist.argmin(axis=1)              # which node each attractor pulls
min_dist = dist.min(axis=1)                     # how far away that closest is
```
</CodeBlock>

The `[:, None, :]` and `[None, :, :]` reshapes broadcast the attractors and nodes into a `(n_a, n_n, 2)` tensor of pairwise vectors. `argmin(axis=1)` collapses the node axis, leaving one closest-node index per attractor.

<Admonition type="important">
For `n_a = 1400, n_n = 1000`, this is 1.4 million pairwise distances per iteration. NumPy does it in ~30 ms. The pure-Python loop equivalent would take ~30 seconds — a thousand-times speedup from one broadcast.
</Admonition>

### Concept 3 — Aggregate, normalise, step

Each node may have *multiple* attractors choosing it. The growth direction is the **mean of unit vectors** from the node toward those attractors — not the mean of positions. (Mean-of-positions would be biased toward distant attractors.)

<CodeBlock lang="python" file="aggregate_demo.py">
```python
directions = {i: [] for i in range(len(nodes))}
for a_local, (c, d) in enumerate(zip(closest_node, min_dist)):
    if d > INFLUENCE_RADIUS:
        continue                                  # too far to influence
    v = attractors[active_idx[a_local]] - nodes[c]
    directions[c].append(v / np.linalg.norm(v))   # unit vector
```
</CodeBlock>

A node with one nearby attractor grows straight toward it. A node with three attractors at different directions grows toward their angular mean. A node with attractors equally distributed in two opposite directions has a mean direction near zero — it does not grow at all this step. That last case is *naturally* where the tree bifurcates: the two opposed pulls produce zero net growth, so the node sits still, and a slightly later iteration with new geometry breaks the tie one way or another.

<Admonition type="note">
"Bifurcation by stall" is one of the algorithm's most elegant properties — branching is not coded explicitly, it emerges from competition between attractors. This is what gives space-colonisation trees their natural-looking branch points compared to L-systems.
</Admonition>

Download `space_colonization.py` and run it. It writes `space_colonization.gif`.

<Download href="/lessons/5.4.3/space_colonization.py" label="space_colonization.py — complete reference implementation" />

**Reflection questions**

- Why does the tree visibly bifurcate at certain points rather than just curving?
- What happens to nodes that are "behind" the growth front?
- Why are most consumed attractors near the centre of the tree rather than at its edges?

<Dropdown summary="Answers">

**Bifurcations** — when one node has attractors pulling in two different directions, the *mean* of those unit vectors has a smaller magnitude than either individual pull. After re-normalisation the step is still `SEGMENT_LENGTH`, but the mean direction points "between" the two pulls. Once the tree advances, the next iteration's geometry assigns different attractors to different child nodes, and the bifurcation completes.

**Old nodes** — they never move again. Once a node is created, it is permanent. New nodes are added but old nodes stay. This is what gives the tree its history — every node's position records where the tree was at some past moment.

**Consumed near centre** — attractors are consumed when a node grows within `KILL_RADIUS` of them. The first attractors to be consumed are the ones closest to the root, then the next closest, and so on. By the end, the bulk of the consumed attractors are in the interior of the tree's reach.

</Dropdown>

</Exercise>

<Exercise n={2} kicker="MODIFY" title="Shape the canopy">

**Goals**

1. **Wide tree**: scatter attractors in a horizontal band rather than a half-disc. The tree grows wide.
2. **Multiple seeds**: start with 3 root nodes 80 px apart. They compete for attractors in the centre and form a forest.
3. **Tight, dense branching**: reduce `INFLUENCE_RADIUS = 30`. The tree branches more frequently because each node only sees nearby attractors.
4. **Long, sparse branching**: increase `INFLUENCE_RADIUS = 120`. The tree extends long branches because distant attractors all funnel to one node.

<Dropdown summary="Goal 1 — what to expect">

A horizontal-spreading tree, like a savanna acacia. The structure has fewer obvious bifurcations because attractors are spread along one direction; most steps pull mostly one way.

</Dropdown>

<Dropdown summary="Goal 2 — what to expect">

Three trees compete. Whichever seed is closest to a region of attractors gets to claim those attractors first. The boundary between trees is sharp because attractors are exclusive.

</Dropdown>

<Dropdown summary="Goal 3 — what to expect">

Dense, branchy tree. Each node only "sees" a small neighbourhood, so the moment a node's local attractor is consumed it must branch into a new direction.

</Dropdown>

<Dropdown summary="Goal 4 — what to expect">

A spindly tree with long branches. Each node sees many attractors and most pull in similar directions, so it grows in a straight line for many segments before bifurcating.

</Dropdown>

</Exercise>

for atr_local, (cn, d) in enumerate(zip(closest_node, min_dist)):
    if d > INFLUENCE_RADIUS:

<Dropdown summary="Hint — consume step">

```python
new_arr = np.array(nodes)
for atr_local in active_idx:
    d = np.linalg.norm(new_arr - attractors[atr_local], axis=-1).min()
    if d < KILL_RADIUS:
        consumed[atr_local] = True
```

Run *after* the new nodes have been added — the just-spawned node is what triggers most attractors to be consumed.

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

Space colonisation grows trees by competition between attractors and tree nodes. Each iteration: every active attractor picks its closest node; each node accumulates a mean direction from the attractors that picked it; each node spawns one new node along that mean direction; attractors close to any node are consumed. The flat-array data structure and broadcasted closest-pair computation are what make the simulation fast. The resulting trees are visually distinct from L-system trees in exactly the right way: branchier where opportunity is dense, straight where it is sparse, terminating naturally where attractors run out.

</Admonition>

**Common pitfalls to avoid**

- Mean of *positions* instead of *unit vectors*. Distant attractors dominate; the tree biases toward them and looks unbalanced.
- No influence radius. Every attractor pulls every node; the tree fans out toward all attractors at once with no branching.
- No consume step. Attractors keep pulling forever; nodes oscillate between regions.
- Re-running consume *before* the new nodes are appended. New nodes do not get to consume the attractors they just created themselves for.
- Pure-Python closest-pair loop. 1.4 million pairwise distances in a Python loop ≈ 30 seconds per frame; in NumPy ≈ 30 ms.
