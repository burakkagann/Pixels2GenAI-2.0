## Big Question — *how do you get NumPy out of and back into a Script TOP without paying a copy tax?* <a id="big-question"></a>

Lesson 10.3.1 introduced Script TOPs as an escape hatch into Python. This lesson is about the mechanics: *the data contract*. TD speaks `float32 RGBA in [0, 1]` shape `(H, W, 4)`; NumPy can produce any dtype and shape. Mismatches cost a copy each frame, and at 1080p a copy is several milliseconds — enough to drop your frame rate. The skill is knowing the contract by heart, designing your NumPy pipeline around it, and using the in-place patterns that avoid copies altogether. The same patterns transfer to other Python-as-extension contexts: PyTorch GPU tensors moving in and out of OpenGL, OpenCV frames flowing into matplotlib, anywhere you have a stable numerical kernel surrounded by an external system.

### Learning objectives

<ol class="obj-list">
  <li>State TouchDesigner's TOP data contract: float32, RGBA, shape (H, W, 4), values in [0, 1].</li>
  <li>Read TOP inputs as NumPy arrays via `op.numpyArray(delayed=False)` and write outputs via `scriptOp.copyNumpyArray(arr)`.</li>
  <li>Identify the four common dtype/shape mismatches and how to fix each.</li>
  <li>Use pre-allocated output buffers to eliminate per-frame allocations.</li>
</ol>

## Part 1 — The data contract <a id="part-1"></a>

Every TOP holds its pixels as `float32 RGBA` in `[0, 1]`. When you read a TOP from Python, that is the shape and dtype you get; when you write a TOP from Python, that is the shape and dtype TD expects. The four-channel layout is mandatory — even a grayscale TOP is `(H, W, 4)` with R=G=B set and A=1.

<CodeBlock lang="python" file="contract_demo.py">
```python
def onCook(scriptOp):
    inp = scriptOp.inputs[0].numpyArray(delayed=False)
    # inp.dtype == float32; inp.shape == (H, W, 4); inp values in [0, 1]
    out = process(inp)
    # out must also be float32, shape (H, W, 4), values in [0, 1]
    scriptOp.copyNumpyArray(out)
    return
```
</CodeBlock>

`delayed=False` returns the current frame's pixels synchronously. `delayed=True` returns the previous frame's pixels but avoids a GPU stall — useful when one Script TOP reads from another in a tight loop.

If your NumPy pipeline produces `uint8` (the PIL/OpenCV default), divide by 255 to get `float32` `[0, 1]`. If your pipeline produces `(H, W, 3)`, you must add an alpha channel — `np.dstack([rgb, np.ones((H, W), np.float32)])` is the standard recipe.

<Admonition type="dyk" title="Did you know? · The HDR motivation">
The `float32` choice (rather than the `uint8` you might expect from Image-1.0 days) lets TD operators work in HDR — values outside `[0, 1]` are kept and can be reduced later by tone-mapping. Bloom, blur of bright sources, exposure adjustment — all assume you have not clamped intermediate values. TD's contract pushes you toward HDR-safe code by default [1].
</Admonition>

## Part 2 — Four common mismatches <a id="part-2"></a>

**1. `uint8` instead of `float32`.** OpenCV reads images as `uint8 [0, 255]`. Fix: `(img.astype(np.float32) / 255.0)`.

**2. `(H, W, 3)` instead of `(H, W, 4)`.** PIL and most image libraries drop alpha for opaque images. Fix: `np.dstack([rgb, np.ones((H, W), np.float32)])`.

**3. `(H, W)` grayscale instead of `(H, W, 4)`.** scikit-image and SciPy often return single-channel. Fix: `gray[..., None].repeat(4, axis=-1)`, then set alpha to 1.

**4. Range outside `[0, 1]`.** Normalisation, mean subtraction, or arithmetic can leave the array outside the canonical range. The pixel still displays (TD clamps for display) but downstream operators may misbehave. Fix: explicit `np.clip(out, 0, 1)`.

<CodeBlock lang="python" file="canonicalise.py">
```python
def canonicalise(arr):
    """Convert any reasonable NumPy image into TD's expected format."""
    if arr.ndim == 2:
        arr = arr[..., None].repeat(4, axis=-1)
    elif arr.shape[-1] == 3:
        h, w = arr.shape[:2]
        alpha = np.ones((h, w, 1), dtype=arr.dtype)
        arr = np.concatenate([arr, alpha], axis=-1)
    if arr.dtype != np.float32:
        if arr.dtype in (np.uint8,):
            arr = arr.astype(np.float32) / 255.0
        else:
            arr = arr.astype(np.float32)
    return np.clip(arr, 0, 1)
```
</CodeBlock>

A single helper like this, used at every `Script TOP` boundary, eliminates 90% of "why does the output look wrong" issues.

## Part 3 — Avoiding per-frame allocations <a id="part-3"></a>

The hidden cost in Script TOP throughput is not the operations themselves — NumPy is fast — but the *allocations*. Every `np.zeros`, `np.empty`, or `array.astype()` allocates a new buffer. At 1080p RGBA float32 that is 32 MB, and the OS allocator is not optimised for hot-path allocation.

The cure: pre-allocate output buffers as module-level globals, fill them in-place each frame.

<CodeBlock lang="python" file="preallocated.py">
```python
import numpy as np

# allocated once at module load
output_buffer = None

def onCook(scriptOp):
    global output_buffer
    inp = scriptOp.inputs[0].numpyArray(delayed=False)
    if output_buffer is None or output_buffer.shape != inp.shape:
        output_buffer = np.empty_like(inp)
    np.add(inp[..., 0:3], 0.1, out=output_buffer[..., 0:3])  # in-place
    output_buffer[..., 3] = 1.0
    scriptOp.copyNumpyArray(output_buffer)
    return
```
</CodeBlock>

`np.add(a, b, out=c)` and similar `out=` overloads write into the pre-allocated buffer without any allocation. Same for `np.multiply`, `np.subtract`, `np.divide`, `np.clip`, and most ufuncs.

The shape check is essential — if the input TOP's resolution changes mid-show (a user adjusts a Resolution TOP), the pre-allocated buffer no longer fits and you need to re-allocate.

<Admonition type="important">
A common mistake: using `output_buffer = func(input)` instead of `func(input, out=output_buffer)`. The first allocates a new array and rebinds the name. The second writes into the existing buffer. The first defeats the purpose of pre-allocation.
</Admonition>

## Synthesis project — round-trip a NumPy edge detector <a id="synthesis"></a>

Build a Script TOP that takes a webcam input, converts to grayscale, runs a Sobel edge detector via `scipy.ndimage.sobel`, then converts back to RGBA. Profile two versions: one with per-frame allocations (the natural code), one with pre-allocated output buffers and `out=` everywhere. Compare cook times.

**Reflection questions**

- Your Script TOP takes 12 ms per frame at 1080p. You apply pre-allocation; the time drops to 6 ms. What is the saved time, and why is it close to half?
- The input TOP is grayscale (single channel internally) but `numpyArray` still returns shape `(H, W, 4)`. Why?
- You change resolution from 720p to 4K mid-show. What error do you see if you forgot the shape check, and what is the fix?

<Dropdown summary="Answers">

**Why ~half savings** — at 1080p × float32 RGBA, every allocation is 32 MB. Modern OS allocators handle that in ~3-6 ms in the average case (worse if memory is fragmented). With three allocations per frame (intermediate temporaries), saving them recovers 9-18 ms. The 6 ms drop reflects the per-frame allocator cost.

**Always 4 channels** — TD internally always exposes TOPs as 4-channel RGBA for uniformity. The grayscale TOP duplicates the single value across R, G, B and sets A=1. Your Python sees the standard shape regardless of internal storage.

**Resolution-change error** — `ValueError: could not broadcast input array from shape (1080, 1920, 4) into shape (720, 1280, 4)`. The fix is the shape check shown above: if `output_buffer.shape != inp.shape`, reallocate.

</Dropdown>

#### Make it your own

- **Compare data paths**: read the same TOP via `numpyArray(delayed=False)` vs `delayed=True`. Profile both. Delayed is the right default unless you need same-frame data.
- **CV2 round trip**: bring a webcam in, convert to OpenCV's BGR, run a `cv2.GaussianBlur`, convert back. The trip costs about 2 ms at 1080p; that is your overhead before any algorithmic work.
- **PyTorch round trip**: copy the NumPy array to a PyTorch CUDA tensor, run a small model, copy back. The PyTorch GPU upload/download is 4-8 ms at 1080p — the limiting factor for tiny networks.

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

TouchDesigner TOPs use `float32 RGBA` in `[0, 1]` shape `(H, W, 4)`. Read with `op.numpyArray(delayed=False)`, write with `scriptOp.copyNumpyArray(arr)`. Convert dtype, channel count, and range at the Python boundary. Pre-allocate output buffers as module globals and use `out=` overloads to avoid per-frame allocations. At 1080p, pre-allocation can halve the frame time of a NumPy-driven Script TOP. The same patterns generalise to any "fast outer system + Python kernel" architecture — OpenCV, PyTorch, ONNX, scikit-image.

</Admonition>

**Common pitfalls to avoid**

- Forgetting to convert `uint8` to `float32`. The output is correct in shape but renders as washed-out / dark.
- Stripping the alpha channel. TD displays as expected but blending downstream goes wrong.
- Allocating output arrays each frame. Cook time doubles for nothing.
- Hard-coding the resolution in the script. Breaks at the first project that uses a different input size.
- Writing `out = func(in)` when you meant `func(in, out=out)`. The first allocates a fresh array; the second uses the pre-allocated buffer.
