## Big Question — *what is the budget for one frame?* <a id="big-question"></a>

At 60 frames per second, you have exactly **16.67 milliseconds** to do everything: cook every operator, resolve every parameter expression, render every viewer, drive every output. If the network takes 17 ms one frame, the next frame starts late, the cook rate drops to 58 fps, and the audience sees stutter. The job of performance monitoring is to find the operators that eat your budget and either make them cheaper or run them less often. This is **the** survival skill for live performance — and it is much closer to game-engine profiling than to Python optimisation, because you are racing a real-time clock, not measuring overall throughput.

### Learning objectives

<ol class="obj-list">
  <li>Compute the per-frame budget from the target frame rate, and recognise the difference between *throughput* and *real-time* optimisation.</li>
  <li>Use TouchDesigner's Performance Monitor to identify the operators consuming the largest share of the frame.</li>
  <li>Apply the five-step optimisation hierarchy: lower resolution, instance, cache, cull unused branches, push work to the GPU.</li>
  <li>Distinguish CPU-bound from GPU-bound bottlenecks — and recognise that the cures are different.</li>
</ol>

## Part 1 — Frame-rate budgets and the cook clock <a id="part-1"></a>

A simple division gives the budget. At target frame rate `f` in fps, the per-frame budget is `1000 / f` milliseconds:

| Target fps | Budget |
| ---------- | ------ |
| 24 (film)  | 41.67 ms |
| 30         | 33.33 ms |
| 60 (default) | 16.67 ms |
| 120 (VR)   | 8.33 ms |
| 240 (high-refresh) | 4.17 ms |

TouchDesigner's default `Cook Rate` is 60 fps. The `Performance Monitor` (`Dialogs → Performance Monitor`, or `Alt+Y`) shows you the actual cook time per frame, broken down by operator. If the total exceeds the budget, the cook rate falls to whatever the network can sustain.

The cook rate falling is *worse* than running at a fixed lower rate. Variable frame rates produce visible stutter; consistent 30 fps looks better than oscillating between 60 and 30. Pick a realistic target up front and design within it.

<Admonition type="dyk" title="Did you know? · Game-engine roots">
The "frame budget" language is borrowed from game engine programming. *id Software's* technical post-mortems of *Doom* (1993) and *Quake* (1996) introduced the practice of breaking the 16-ms frame into named compartments — physics, AI, sound, rendering. TouchDesigner inherits the same discipline because, for real-time visuals, the constraint is identical [1].
</Admonition>

## Part 2 — Reading the Performance Monitor <a id="part-2"></a>

The Performance Monitor displays a table with one row per operator showing **cook time** (microseconds spent cooking that operator this frame), **cooks per frame** (usually 1, but caches and feedback loops can cook multiple times), and **percent of frame** (cook time divided by total frame time).

The trick to reading it: **sort by cook time, look at the top five rows.** Those five usually account for 60–90% of the frame. Optimising anything outside the top five is wasted effort.

Common hot operators:

- **Composite TOP** at high resolution — the per-pixel work scales with `H × W`.
- **Glsl Multi TOP** with complex shaders — GPU time can blow up on a slow card.
- **Particle SOP** with thousands of particles — CPU geometry processing.
- **Script DAT cooking every frame** — Python is much slower than native operators.
- **Movie File In TOP** with 4K HDR sources — decode + upload bandwidth.

<Admonition type="important">
**Cook time is wall-clock time**, not CPU time. A TOP that uses the GPU may show low cook time but still cost a lot if the GPU is the bottleneck. Use external tools (Nvidia Nsight, RenderDoc) to confirm GPU-side bottlenecks.
</Admonition>

## Part 3 — The five-step optimisation hierarchy <a id="part-3"></a>

In rough order from cheapest to most invasive:

**1. Lower resolution.** A `Resolution TOP` set to `1280 × 720` instead of `3840 × 2160` cuts per-pixel work by 9×. Often invisible to the audience; always worth trying first. Render the final composite at high resolution and the upstream pipeline at lower.

**2. Instance, do not duplicate.** Drawing 1000 copies of a sphere is one of two things: 1000 `Geometry COMP` instances (terrible) or one `Geometry COMP` with `instancing` set to a CHOP of positions (great). Instancing batches the draw call; duplication does not.

**3. Cache.** A `Cache TOP` stores the previous frame's output and re-uses it when inputs have not changed. Wrap any operator that does expensive work but rarely changes its output (e.g., a `Text TOP` rendering a string that updates once per minute) in a Cache TOP that re-cooks only on change.

**4. Cull unused branches.** TouchDesigner cooks any branch with a downstream viewer or parameter reference. If a branch is currently not contributing to the visible output, set its `Cook Type` to `Off` or `Always` based on whether you need it at all. The `Selective` cook type cooks only when explicitly triggered.

**5. Push work to the GPU.** A Composite TOP, Blur TOP, Convert TOP — all run on the GPU. A Python `Script TOP` running NumPy code runs on the CPU. For per-pixel operations the GPU is 10–100× faster. If you must do custom per-pixel work, write a `GLSL TOP` shader rather than a Script TOP.

| Bottleneck      | Symptom                          | First fix                       |
| --------------- | -------------------------------- | ------------------------------- |
| CPU-bound       | Performance Monitor shows ops summing to >16ms | Cache, lower res, push to GPU |
| GPU-bound       | Low op cook times, still dropping frames | Lower resolution, simplify shaders |
| Memory-bound    | Frame drops correlate with allocations | Pre-allocate, re-use textures |
| Driver-bound    | Stutter on specific operators, mostly fine | Update drivers, check vendor forums |

<Admonition type="note">
The single highest-leverage optimisation in 90% of cases: **lower the rendering resolution**. Find the *output* resolution your venue actually requires (often 1080p or 720p), and design the rest of the network at that resolution or below. Designing for 4K when the projector is 1080p is a free 4× cost increase for nothing.
</Admonition>

## Synthesis project — diagnose and optimise a slow network <a id="synthesis"></a>

Build (or download) a deliberately overweight TD network — high-resolution Noise + multiple Blur passes + a Script TOP doing NumPy work + several Composite TOPs at 4K. Open the Performance Monitor, identify the top-five cost operators, and apply the optimisation hierarchy in order. Document the cook time *before* and *after* each step. The goal: cut total frame time by at least 50% without changing the visible output.

**Reflection questions**

- Why is "lower the resolution" almost always the first thing to try?
- A Script TOP with NumPy operations shows 8 ms cook time. Is it CPU-bound or GPU-bound?
- The Performance Monitor shows all operators cooking in well under the budget, but the cook rate still drops. What else could be wrong?

<Dropdown summary="Answers">

**Lower resolution** — per-pixel operators (Blur, Composite, Convert) scale as `H × W`. Cutting resolution from 4K to 1080p divides their cost by 4. Almost everything else is more invasive. *Try this first.*

**Script TOP CPU-bound** — yes. Script TOP runs Python on the CPU. NumPy operations run on the CPU (unless you explicitly use `cupy` or similar). The fix: rewrite as a GLSL TOP for per-pixel work, or move the logic into a CHOP that runs less often.

**Hidden cause** — VSync waiting for monitor refresh; driver-side rate limiting; another process competing for GPU; OS-level interrupts (anti-virus, indexing, drivers). External tools (Task Manager, RTSS, GPU profiler) are the cure.

</Dropdown>

#### Make it your own

- **A/B test resolutions** at the output. Render the same network at 720p, 1080p, 1440p. Find the resolution where your hardware first drops frames.
- **Cache and warm up** every expensive operator at project load. The first frame is always the slowest; pre-cooking removes the spike.
- **Pin one monitor to the network and another to the Performance Monitor**. Watching the cook time scroll while you adjust the network is the fastest way to develop intuition for cost.

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

Real-time visuals are constrained by the frame budget — 16.67 ms at 60 fps. The Performance Monitor breaks the budget into per-operator cook times; the top five rows account for most of the frame. The optimisation hierarchy in rough order: lower resolution, instance, cache, cull unused branches, push to GPU. The biggest mistake is designing for 4K when the output is 1080p. The second biggest is doing per-pixel work in Python instead of GLSL. Consistent 30 fps reads better than wandering 30–60. Pick a target, profile, optimise top-five operators, repeat.

</Admonition>

**Common pitfalls to avoid**

- Optimising without profiling. The slowest operator is usually not the one you think it is.
- Targeting 60 fps on hardware that comfortably hits 30. Use a fixed cook rate of 30 if 60 is unreliable.
- Running Script TOPs for per-pixel work. Always rewrite as GLSL TOP if performance matters.
- Letting the Performance Monitor stay open during performance. The monitor itself costs cook time.
- Believing one machine's profile predicts another's. Always profile on the production hardware.
