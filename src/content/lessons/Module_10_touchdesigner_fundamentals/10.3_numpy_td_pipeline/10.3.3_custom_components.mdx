## Big Question — *how do you stop rebuilding the same network twenty times?* <a id="big-question"></a>

Every TouchDesigner artist builds the same kind of network repeatedly: a noise generator with a few tweakable parameters, a particle effect with brightness and density knobs, an audio reactivity module. Copy-pasting the network into every project is the obvious thing to do, but it has two problems: (1) updating the design later means editing every copy, and (2) the parameters that should be tunable are buried among 20 internal parameters that should not be. The cure is **custom Components**. Wrap your sub-network in a `Base COMP`, define **custom parameters** on the COMP itself that the network's internals reference, and the result is a reusable unit with a clean interface. Save the COMP to a `.tox` file and you can drop it into any project from now on. This is TouchDesigner's mechanism for abstraction, encapsulation, and reuse — the unit of reuse is the Component, not the operator.

### Learning objectives

<ol class="obj-list">
  <li>Identify Base COMP and Container COMP as the two main component types — invisible (logic) and visible (UI).</li>
  <li>Add **custom parameters** to a COMP and reference them from operators inside using `me.parent().par.X`.</li>
  <li>Save and load components as `.tox` files for cross-project reuse.</li>
  <li>Design the "public interface" of a component — what to expose, what to hide.</li>
</ol>

## Part 1 — Base COMP vs Container COMP <a id="part-1"></a>

Both are containers; both can hold an arbitrary sub-network. The difference is visibility:

- **Base COMP** — an *invisible* container. No on-screen presence. Use for *logic* components: an audio analyser, a parameter controller, a state machine.
- **Container COMP** — a *visible* container. Has width, height, and renders a `Background TOP`. Use for *UI* components: a panel, a button, a slider.

For this lesson we focus on Base COMP because logic-only components are the more common reuse target. UI components are the subject of lesson 10.4.1.

To create one: press **Tab → COMP → Base**. The COMP appears as a single node on your canvas. Double-click to dive in; you are now inside its sub-network. Build the sub-network normally — TOPs, CHOPs, whatever.

<Admonition type="dyk" title="Did you know? · TD components and Unity prefabs">
The Base COMP / `.tox` workflow is conceptually identical to Unity's prefab system and Unreal's blueprint actor system. All three exist for the same reason: in a system with many tunable components, you need a *unit of versioned reuse* that is bigger than a single operator. The `.tox` extension stands for "TouchDesigner Operator Xport" — Derivative's choice in 2008 [1].
</Admonition>

## Part 2 — Custom parameters: the public interface <a id="part-2"></a>

The trick that makes a component genuinely reusable is **custom parameters**: parameters you add to the COMP itself that the internal operators reference. From outside, the COMP has a clean parameter page; from inside, the operators look up those parameters via `me.parent().par.X`.

To add custom parameters:

1. Open the **Component Editor** (right-click on the COMP → Customize Component, or `Alt+C`).
2. Add parameters: name, type (float, int, menu, RGB, file), default, min/max.
3. Save.

Now the COMP has those parameters on its parameter page. Inside the COMP, reference them in expressions:

<CodeBlock lang="python" file="param_reference.py">
```python
# inside a child operator's parameter expression
me.parent().par.Brightness        # the custom parameter named "Brightness"

# inside a Script DAT
brightness = parent().par.Brightness.eval()
op('level1').par.brightness = brightness
```
</CodeBlock>

The convention is to capitalise the first letter of custom parameter names (`Brightness`, not `brightness`) so they sort distinctly from built-in parameters. Internal references use exactly that capitalisation.

Designing the public interface is mostly about *deciding what NOT to expose*. A noise component might have 30 internal parameters across 8 internal operators; the public face should be 3-6 conceptually meaningful knobs: amplitude, frequency, evolution speed, colour palette. The rest stay locked inside.

<Admonition type="important">
Custom parameters that need to *animate* should be set up with their default expression already present. Otherwise users of your component will have to dig into the network to figure out how to animate them. Provide animation hooks as documented part of the interface.
</Admonition>

## Part 3 — Saving and loading `.tox` files <a id="part-3"></a>

To save a Base COMP for cross-project reuse: right-click the COMP → **Save Component .tox**. Pick a filename and folder. The COMP and its entire sub-network are written to disk as a single `.tox` file.

To load: in any project, **Tab → COMP → External**, then point at the `.tox`. The COMP loads as a node, with the entire saved sub-network inside. Custom parameters are preserved.

A few production conventions:

- **Versioning**: include a version suffix in the filename (`noise_panel_v2.tox`). When you ship an update, the old version of any project still works because it references the old `.tox`.
- **Storage location**: keep `.tox` files in a project-relative folder (`tox/` or `components/`). Avoid absolute paths; they break the moment a project moves to another machine.
- **Documentation**: add a `Text DAT` inside the component with usage notes. Users will find it; the alternative is recreating tribal knowledge per project.

<Admonition type="note">
Some studios keep a shared component library on a network drive or Git repository, with one folder per component, versioned. A `.tox` file is binary, so Git LFS handles diffs better than text diffs. Larger teams treat components as software artefacts: they have changelogs, release tags, and migration notes.
</Admonition>

## Synthesis project — wrap your boids in a reusable component <a id="synthesis"></a>

Take your boids network from lesson 10.2.2 (or build a new one). Wrap it in a Base COMP. Expose four custom parameters: `Numagents`, `Separationweight`, `Alignmentweight`, `Cohesionweight`. Save as `boids_v1.tox`. In a new project, load the `.tox` and verify the parameters behave as expected. The component is now a tool you carry between projects.

**Reflection questions**

- Why do custom parameter names start with a capital letter by convention?
- Your component has an internal Script DAT that needs to know its own component's parameters. How does it reference them?
- The component you saved a month ago no longer fits your needs. How do you update existing projects that use it?

<Dropdown summary="Answers">

**Capitalisation** — the TouchDesigner UI sorts capitalised parameters above lowercase built-ins. The convention makes custom parameters visible at a glance and avoids name collisions with future built-in parameters.

**Reference from inside** — `parent().par.X`. The `parent()` call returns the containing COMP; `.par.X` is the custom parameter. Use `op('..').par.X` for a slightly different idiom that does the same thing.

**Updating** — two strategies. (1) Increment the version: save the new `.tox` as `_v2.tox`; existing projects keep using `_v1.tox`; new projects use `_v2.tox`. (2) Overwrite `_v1.tox`: every project picks up the change next load. Strategy 1 is safer for production; strategy 2 is fine for in-progress work.

</Dropdown>

#### Make it your own

- **Audio-reactive panel**: a Base COMP that takes an audio signal in, exposes "Bass", "Mids", "Treble" channels out. Wire any visual into those channels for instant reactivity.
- **Preset bank**: a Base COMP with 8 preset slots, each storing a snapshot of internal state. Custom parameter "Active Preset" selects which to use. (See lesson 10.4.3 for the full preset system pattern.)
- **Library directory**: create `~/td-components/` and start filling it with one `.tox` per useful subnetwork. Within a year you have a personal toolkit.

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

Base COMP and Container COMP are TouchDesigner's containers. Wrap any reusable sub-network in a Base COMP; expose only the parameters that should be tunable as custom parameters; reference them from inside with `parent().par.X`. Save to `.tox` for cross-project reuse. The skill is interface design: what *not* to expose. Custom Components are the unit of abstraction and reuse in TD, equivalent to Unity prefabs or Unreal blueprints. A library of `.tox` files is the accumulated knowledge of every successful TD artist — start building yours today.

</Admonition>

**Common pitfalls to avoid**

- Exposing every internal parameter as custom. Defeats the abstraction; the public interface should be small.
- Hard-coding paths inside components. Use relative paths (`me.parent()` patterns).
- Forgetting versioning. When you ship a breaking change, existing users get silent corruption.
- Saving `.tox` files inside `dist/` or another build folder. Use a stable project-relative path.
- Mixing Base COMPs (invisible) with Container COMPs (visible) without intention. Pick the right kind for the job.
