## Overview <a id="overview"></a>

The music visualizer is one of the great cultural objects of the late 1990s: every Windows machine had Winamp's classic "AVS" plugins, every iTunes 6.0 user knew the swirling psychedelic "iTunes Visualizer," every Mediaplayer-era PC had MilkDrop spinning fractals to the beat. Modern descendants are Spotify Canvas, Apple Music album visualizers, and every shader-driven music-reactive piece on Shadertoy.

The mechanical architecture is two distinct stages: **(1) audio analysis** — extract a frequency spectrum from the audio signal via FFT — and **(2) visualization** — render shapes whose parameters depend on the spectrum. This lesson focuses on the *rendering* stage with a fake, synthesised spectrum, so you can build the visualizer without learning audio DSP first. Plugging in a real WAV's FFT is a one-function swap.

### Learning objectives

<ol class="obj-list">
  <li>Synthesize a 64-bin frequency spectrum that pulses on bass, mid, and treble bands at different rhythms.</li>
  <li>Render a **radial spectrum**: bars radiating outward from a central disc, length proportional to amplitude.</li>
  <li>Render a **horizontal spectrum**: vertical bars from a baseline, height proportional to amplitude, colour by amplitude.</li>
  <li>Recognise the audio/render decoupling: any spectrum source (FFT, synth, file) drives any visualizer.</li>
</ol>

## Quick start — two visualizers <a id="quick-start"></a>

<CodeBlock lang="python" file="quick_start.py">
```python
import math, numpy as np
from PIL import Image, ImageDraw

def fake_spectrum(frame, n_bins=64, n_frames=90):
    t = frame / n_frames
    bins = np.zeros(n_bins, dtype=np.float32)
    bins[:8]   = (0.6 + 0.4 * np.sin(2*np.pi * t * 4)) * np.linspace(1, 0.5, 8)
    bins[8:32] = (0.5 + 0.4 * np.sin(2*np.pi * t * 8 + 0.6)) * (0.7 + 0.3*np.sin(np.arange(24)*0.4))
    bins[32:]  = (0.4 + 0.3 * np.sin(2*np.pi * t * 16 + 1.2)) * (0.6 + 0.4*np.random.default_rng(frame*13).random(32))
    return bins.clip(0, 1)
```
</CodeBlock>

## Core concepts <a id="core-concepts"></a>

### Concept 1 — The spectrum as the universal data structure

Every audio visualizer's input is a per-frame array of amplitudes — typically 32, 64, 128, 256, or 512 bins, each representing a frequency range. The bin amplitudes are produced by an **FFT** (Fast Fourier Transform) of a window of audio samples. For our purposes, we synthesise the spectrum without doing the FFT:

<CodeBlock lang="python" file="spectrum.py">
```python
def fake_spectrum(frame, n_bins=64, n_frames=90):
    t = frame / n_frames
    bins = np.zeros(n_bins, dtype=np.float32)
    # Bass band — first 8 bins
    bins[:8] = (0.6 + 0.4 * np.sin(2*np.pi * t * 4)) * np.linspace(1, 0.5, 8)
    # ...
    return bins.clip(0, 1)
```
</CodeBlock>

Three modulators driven by different rhythms give the synth a believable "song" feel. Replace with `scipy.fft.fft` of a real audio buffer and the rest of the pipeline doesn't change.

### Concept 2 — Radial spectrum: polar layout

The radial visualizer places each bar on a circle, radiating outward from a centre. Each of the 64 bins gets an angular slot of `360° / 64`. Polar coordinates make the layout one line each per endpoint:

<CodeBlock lang="python" file="radial.py">
```python
for i, amp in enumerate(spectrum):
    angle = 2 * math.pi * i / n_bins - math.pi / 2
    inner = (cx + inner_r * cos(angle), cy + inner_r * sin(angle))
    outer = (cx + outer_r(amp) * cos(angle), cy + outer_r(amp) * sin(angle))
    draw.line([inner, outer], fill=color_for(i), width=4)
```
</CodeBlock>

Colour bands distinguish bass (warm), mid (green), and treble (cool). The visual is the spectrum equivalent of a **clock face**: each bin gets a fixed angular position, the amplitude controls the radius.

<Admonition type="dyk" title="Did you know · the iTunes Visualizer was a particle engine">
The iconic iTunes 6.0 visualizer used a particle-based field driven by the audio spectrum: each FFT bin spawned particles whose speed and colour depended on the bin's amplitude. The kaleidoscopic look came from rendering on a slowly-rotating polar grid. The whole thing ran at 60fps on a 2005-era G5 PowerMac because the rendering was done in OpenGL. Apple removed it in iTunes 10 (2010) because, per the design team's later comments, "nobody opened the visualizer anymore" [1].
</Admonition>

### Concept 3 — Horizontal spectrum: Cartesian layout

The horizontal visualizer is the classic Winamp look: vertical bars from a baseline at the bottom, height proportional to amplitude. Same data, different layout:

<CodeBlock lang="python" file="horizontal.py">
```python
bar_w = canvas_w // n_bins
for i, amp in enumerate(spectrum):
    h = int(amp * max_h)
    x0 = i * bar_w + 1
    y0 = canvas_h - 20 - h
    color = green_to_red(amp)
    draw.rectangle([x0, y0, x0 + bar_w - 2, canvas_h - 20], fill=color)
```
</CodeBlock>

Each bar's colour communicates amplitude: green for low amplitudes, yellow for mid, red for peak. This is the **VU-meter** convention — borrowed from analog audio gear of the 1960s. Modern visualizers often add a "peak hold" line that decays after each peak, but the core layout is identical.

<Admonition type="important">
The two visualizers in this lesson take the **same** spectrum array. To add a third visualizer — a circular waveform, a particle field, a 3D bar grid — the new code only needs to read the spectrum array; nothing about the spectrum production has to change. That is the value of the audio/render decoupling.
</Admonition>

## Exercises <a id="exercises"></a>

Three exercises in **Execute → Modify → Create** order: render the visualizers, swap the synthetic music for different rhythms, then build a third visualizer.

<Exercise n={1} kicker="EXECUTE" title="Render the two-panel visualizer">

Run `music_viz.py`. The script generates 90 frames of the side-by-side radial and horizontal spectrum.

<Download href="/lessons/8.4.1/music_viz.py" label="music_viz.py — reference implementation" />

**Reflection questions**

- The bass band uses a 4× temporal frequency, the treble band uses 16×. What does that say about how the synthetic music "feels"?
- The radial visualizer maps bin index to angle. Why does it use `-π/2` as the angular offset?
- Why does the horizontal visualizer use a green-to-red colour gradient based on amplitude rather than on bin index?

<Dropdown summary="Answers">

**Temporal frequencies** — bass on a slow 4× rhythm feels like a kick drum on every beat. Treble on a fast 16× rhythm feels like hi-hats on every sixteenth. The differential rates produce a layered "music with rhythm" feel even though no real audio drove the spectrum.

**Angular offset** — `-π/2` rotates the first bin to the **top** of the circle (12 o'clock). Without the offset, the first bin would be on the right (3 o'clock). Top-aligned visualizers feel more anchored than right-aligned.

**Colour by amplitude** — VU-meter colour communicates *loudness* (the dB level), which is what listeners care about. Colour by bin index would communicate *pitch*, which is information the eye already gets from the bin's horizontal position. Don't double-encode.

</Dropdown>

</Exercise>

<Exercise n={2} kicker="MODIFY" title="Swap the synthetic music">

Three variants of the fake spectrum function.

**Goals**

1. **Steady drone.** Replace all temporal modulation with constant 0.7. The visualizer should look like a steady pattern with no rhythm.
2. **Fast electronic.** Increase all temporal frequencies by 2× (8×, 16×, 32×). The visualizer becomes frantic.
3. **Sparse percussion.** Use `bins[:8] = bass if (frame % 15 == 0) else bass * 0.1`. The bass only fires every 15 frames — a sparse kick drum.

<Dropdown summary="Goal 1 — what to expect">

A motionless visualizer. Looks broken, but actually demonstrates how the rhythm comes from the modulation, not the bars themselves.

</Dropdown>

<Dropdown summary="Goal 2 — what to expect">

Frenetic energy. All bands pulse rapidly; the eye loses the rhythm. Use sparingly — too much modulation is visually exhausting.

</Dropdown>

<Dropdown summary="Goal 3 — what to expect">

A clear "kick drum every 15 frames" pulse. The contrast with the continuous mid and treble bands gives a sense of *song structure* — a periodic beat under a continuous melody.

</Dropdown>

</Exercise>

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

Music visualization decouples audio analysis from rendering: any spectrum source (real FFT or synthetic) drives any visualizer (radial, horizontal, particle, fractal, anything). The spectrum is the universal interface — a per-frame array of bin amplitudes. Polar layouts make radial visualizers trivial; Cartesian layouts make horizontal bars trivial. Colour conveys amplitude (VU-meter convention); position conveys frequency. The architecture scales from a 10-line demo to broadcast-quality visualizers — only the rendering complexity changes.

</Admonition>

**Common pitfalls to avoid**

- **Direct audio access in the render loop.** Couples audio and render — hard to swap either. Pass the spectrum through.
- **Colour by bin index AND amplitude.** Double-encoding wastes a visual channel. Pick one.
- **Bars that flicker every frame.** Without smoothing, the visualizer feels jittery. Use exponential smoothing: `spectrum_smooth = α * spectrum_new + (1 - α) * spectrum_prev` with `α ≈ 0.3`.
- **Too many bins.** 64 is enough for most visualizers. 256 looks busy without adding information; 16 is too coarse for melodic content.
