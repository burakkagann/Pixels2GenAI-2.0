## Overview <a id="overview"></a>

This is Module 11's capstone. Combine everything: a **phone web page** (HTML + WebSocket client) hosts a UI of sliders, knobs, and buttons. The user touches the controls. Each touch sends a JSON message over WebSocket to a **Python backend** running a generative visualization. The backend reads the messages, updates the visualization's parameters, and renders the next frame on the laptop's display.

The pattern is identical to professional VJ rigs running TouchOSC + Resolume — a phone full of touchable sliders sending OSC messages to a desktop renderer — but built entirely with web standards, no proprietary apps. Anyone with a phone in a gallery can scan a QR code and start controlling the installation.

### Learning objectives

<ol class="obj-list">
  <li>Build an HTML/CSS UI with sliders, rotary knobs, and buttons styled for touch.</li>
  <li>Wire each control to a JSON message sent over WebSocket on every change.</li>
  <li>Run a Python WebSocket server that reads the JSON, updates a shared state dictionary, and renders the visualization from the state.</li>
  <li>Recognise the architecture as a touchpad-on-phone + brain-on-laptop split — UI on one device, computation on another.</li>
</ol>

## Quick start — phone UI + Python visual <a id="quick-start"></a>

<CodeBlock lang="python" file="quick_start_server.py">
```python
import asyncio, json, websockets
from PIL import Image, ImageDraw

STATE = {'speed': 0.5, 'density': 60, 'rgb': (180, 120, 220)}

async def handler(ws):
    async for msg in ws:
        update = json.loads(msg)
        STATE.update(update)

async def main():
    async with websockets.serve(handler, '0.0.0.0', 8765):
        await asyncio.Future()

asyncio.run(main())
```
</CodeBlock>

## Core concepts <a id="core-concepts"></a>

### Concept 1 — HTML/CSS for touch UI

Browser-native form controls (`<input type="range">`, `<input type="color">`, `<button>`) work on touch screens with no extra code. For more sophisticated layouts, set `viewport` meta and use `flexbox` for the panel arrangement:

<CodeBlock lang="html" file="phone_ui.html">
```html
<meta name="viewport" content="width=device-width, initial-scale=1, user-scalable=no">
<style>
  body { display: flex; flex-direction: column; gap: 24px; padding: 16px;
         background: #1a1c28; color: #fff; font-family: system-ui;
         touch-action: none; }
  input[type=range] { width: 100%; height: 32px; }
  button { padding: 16px; font-size: 18px; border-radius: 8px;
           background: #60a060; color: #fff; }
</style>
```
</CodeBlock>

`touch-action: none` disables browser scroll/zoom gestures so your sliders work smoothly. The `viewport` meta tag makes the layout fit the phone screen.

For a more polished look, use a CSS framework (Tailwind, Bulma) or a slider library (NoUiSlider for fancier rotary knobs). For a quick prototype, plain HTML is enough.

### Concept 2 — JSON messages over WebSocket

Every UI change sends a single JSON message. Use **delta updates** (only the changed field) to minimise bandwidth and avoid race conditions:

<CodeBlock lang="javascript" file="send.js">
```javascript
const ws = new WebSocket('ws://192.168.1.42:8765')
ws.onopen = () => console.log('connected')

function send(patch) {
  ws.send(JSON.stringify(patch))
}

speed.oninput = () => send({speed: speed.value / 100})
density.oninput = () => send({density: parseInt(density.value)})
color.oninput = () => send({rgb: color.value})
trigger.onclick = () => send({trigger: true})
```
</CodeBlock>

On the Python side, merge each delta into the shared state dictionary:

<CodeBlock lang="python" file="merge.py">
```python
STATE = {'speed': 0.5, 'density': 60, 'rgb': '#a072d8', 'trigger': False}

async def handler(ws):
    async for raw in ws:
        update = json.loads(raw)
        STATE.update(update)
        if update.get('trigger'):
            STATE['trigger'] = False        # auto-reset edge triggers
            schedule_one_shot_effect()
```
</CodeBlock>

The render thread reads `STATE` every frame; the WebSocket handler writes to it. Python's GIL keeps single-key updates atomic.

<Admonition type="dyk" title="Did you know · TouchOSC is the original phone-controller">
TouchOSC (2008) was the first widely-used "iPhone as MIDI controller" app. It sent OSC messages over WiFi to Ableton Live, Resolume, TouchDesigner, and similar VJ tools [1]. The configuration was XML on the desktop; the UI was drag-and-drop on the phone. Modern equivalents: TouchOSC (still alive at v2), Lemur, Mobilizer, OSCulator. The architectural pattern in this lesson — HTML page on phone, WebSocket to Python — is the web-native equivalent that needs no app install [2].
</Admonition>

### Concept 3 — Single-page UI, multiple controllers

Multiple phones can connect to the same WebSocket server simultaneously. Whose UI input takes priority? Two common patterns:

- **Last-write-wins.** Whoever moves a slider last gets to set its value. Simple, sometimes annoying when two users fight over the same control.
- **Per-user channels.** Each connected client gets its own subset of the state. Useful for multi-user installations where different visitors control different elements.

For a single-installation, single-user case, last-write-wins is the right default. For a gallery with many visitors, channelize controls or use a turn-based system.

<CodeBlock lang="python" file="multi_user.py">
```python
clients = {}

async def handler(ws):
    client_id = id(ws)
    clients[client_id] = ws
    try:
        async for raw in ws:
            update = json.loads(raw)
            # Last-write-wins
            STATE.update(update)
            # Echo to all connected clients (so phones stay in sync)
            for c in clients.values():
                if c != ws:
                    await c.send(json.dumps(STATE))
    finally:
        del clients[client_id]
```
</CodeBlock>

<Admonition type="important">
Mobile WebSocket connections die when the phone screen sleeps. Add **reconnect logic** on the client: detect `onclose`, wait a few seconds, open a new WebSocket. Otherwise the gallery visitor's phone goes dark and "stops working" inscrutably.
</Admonition>

**Reflection questions**

- The JSON packet `{slider: 0.8, btn: 1}` is only ~20 bytes. Why is small payload important here?
- The TRIGGER button is shown as edge-triggered (one-shot). How is that different from the slider's continuous values?
- What happens if the phone goes to sleep mid-show?

<Dropdown summary="Answers">

**Small payload** — at 60 Hz update rate, even 1 KB packets would consume 60 KB/s sustained per phone, which adds up across multiple controllers. Small JSON keeps the latency low and the bandwidth modest.

**Edge vs continuous** — the TRIGGER button fires once when pressed (edge); the slider is continuous (every move sends a new value). The server treats them differently — the trigger schedules a one-shot effect; the slider updates a continuous parameter.

**Phone sleep** — WebSocket dies; the Python server's `recv` loop exits for that client; the renderer keeps using the last received values. When the phone wakes, the JS reconnects (if you've written reconnect logic) and resumes control.

</Dropdown>

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

A web-based remote-control surface is the modern equivalent of a hardware MIDI controller. Phone runs an HTML page with sliders/buttons; Python runs a WebSocket server that updates a shared state dictionary; render loop reads the state and draws each frame. JSON delta messages over WebSocket give 60 Hz control with no special apps. Multi-touch and multi-user are first-class. Reconnect on phone sleep is essential. This is the architecture used in every modern interactive installation, every TouchOSC-style VJ rig, and every web-based control panel for an IoT system. Module 11's capstone integrates capture, control, computation, and distribution into one pattern.

</Admonition>

**Common pitfalls to avoid**

- **No reconnect logic.** Phone sleeps; UI stops working with no recovery.
- **Sending full-state every change.** Bandwidth explodes; use delta JSON.
- **No echo from server.** Multi-user installations get out of sync without a state-broadcast loop.
- **Last-write-wins fights.** Two users wrestling over the same slider. Channel controls, or use turn-taking.
