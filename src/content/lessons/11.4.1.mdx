## Overview <a id="overview"></a>

A single GPU can drive 4–8 projectors at 4K@60. Beyond that, you split rendering across multiple machines. The architecture: one **controller** machine generates the shared global state (current frame number, music position, sensor inputs) and broadcasts it to N **renderer** machines over the local network. Each renderer draws its assigned slice of the final image to its connected display. The controller never renders pixels; the renderers never compute global state. This separation is the basis of every large-venue projection-mapping show, every LED ribbon installation, every concert video wall.

The "broadcast a sync packet" part is what this lesson covers. The actual rendering work is whatever you build on top — TouchDesigner, Resolume, Unity, custom Python, anything that can read a UDP packet.

### Learning objectives

<ol class="obj-list">
  <li>Recognise the controller / renderer architecture: one source of truth, N display nodes.</li>
  <li>Use UDP for sync packets (low latency, no connection setup, tolerates drops) rather than TCP.</li>
  <li>Manage clock skew across machines — some renderers will receive the packet a few ms after others.</li>
  <li>Recognise this pattern as the same as DMX (11.3.2), Art-Net, sACN, NDI, and every other "broadcast state to many receivers" protocol.</li>
</ol>

## Quick start — controller broadcasts to 4 renderers <a id="quick-start"></a>

<CodeBlock lang="python" file="quick_start.py">
```python
# Controller side
import socket, struct, time

s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.setsockopt(socket.SOL_SOCKET, socket.SO_BROADCAST, 1)
frame = 0
while True:
    msg = struct.pack('>If', frame, time.time())
    s.sendto(msg, ('192.168.1.255', 6000))     # broadcast to LAN
    frame += 1
    time.sleep(1/60)   # 60 Hz sync rate

# Renderer side
r = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
r.bind(('0.0.0.0', 6000))
while True:
    data, _ = r.recvfrom(1024)
    frame, t = struct.unpack('>If', data)
    render(frame, t)
```
</CodeBlock>

<Admonition type="tip">
The controller doesn't *care* which renderers are listening. It broadcasts to the network and any subscribed receiver handles the packet. Renderers can join or leave the show without restarting the controller — the same property that makes pub/sub messaging robust.
</Admonition>

## Core concepts <a id="core-concepts"></a>

### Concept 1 — UDP for sync, TCP for content

UDP and TCP are the two main internet transport protocols. The right choice depends on what's at stake:

- **TCP** — connection-based, reliable, ordered. Every byte sent arrives in order; lost packets are retransmitted. Cost: latency (round-trip for connection setup; retransmit delays under packet loss) and per-connection state. Use for **content delivery** (asset loading, configuration sync, video streams via custom protocol).
- **UDP** — connectionless, best-effort. Packets may arrive out of order or not at all. No retransmit; no connection state. Use for **time-sensitive sync**: lost packets are better dropped than retransmitted (the missed sync moment has already passed).

For our 60 Hz controller→renderer sync, UDP is the only viable choice. A 100 ms TCP retransmit would arrive 6 frames late — useless. With UDP, if a packet drops, the renderer holds the previous frame's state for one extra frame; no observable glitch.

### Concept 2 — Clock skew and time-coded sync

Different renderer machines receive the same broadcast packet at slightly different times due to network jitter. For 60 Hz content the per-packet skew is ~1–5 ms on a quiet LAN, ~10–50 ms on a busy one. For most visual content this is invisible, but for **high-precision sync** (LED ribbons with sub-pixel temporal accuracy, frame-locked video walls), you need explicit time-coding:

<CodeBlock lang="python" file="time_code.py">
```python
# Controller sends absolute timestamp
msg = struct.pack('>If', frame, time.time())

# Renderer schedules render at the timestamp, not at receive time
data, _ = sock.recvfrom(1024)
frame, target_time = struct.unpack('>If', data)
delay = target_time - time.time()
if delay > 0:
    time.sleep(delay)
render(frame)
```
</CodeBlock>

This pattern is called **time-coded sync** [1]. All renderers wait until the same wall-clock time before rendering. Frame-perfect alignment requires NTP-synchronised clocks on all machines (`chrony` or `ptpd`).

<Admonition type="dyk" title="Did you know · TouchDesigner uses CHOPs for this pattern">
TouchDesigner's `multitouchinCHOP` and `multitouchoutCHOP` operators implement the exact controller-renderer pattern described here, with Network Direct Protocol (NDI) for video and OSC for control. NDI specifically uses **mDNS auto-discovery** so renderers find the controller without manual IP configuration. The Newtek NDI protocol (now Vizrt NDI) is the industry standard for inter-machine video in broadcast and live events [2].
</Admonition>

### Concept 3 — Slicing the work

Each renderer typically owns a portion of the final image. The renderer's index (its slot in the rig) determines which slice it draws:

<CodeBlock lang="python" file="slicing.py">
```python
N_RENDERERS = 4
MY_INDEX = 2          # which renderer am I?
TOTAL_W = 7680        # combined output width across all renderers

# Each renderer draws a vertical strip
strip_w = TOTAL_W // N_RENDERERS
my_x0 = MY_INDEX * strip_w
my_x1 = my_x0 + strip_w

def render(frame_idx, my_index):
    # Compute the global pixels in [my_x0, my_x1) for this frame
    return generate_image(frame_idx, my_x0, my_x1)
```
</CodeBlock>

The controller sends one packet per frame; each renderer applies its own offset. Same pattern handles a single 8K display split across 4 GPUs, a circular dome across 6 projectors, or an LED ribbon across 16 controllers.

<Admonition type="important">
The synchronisation problem is **distributed consensus** in disguise. Production setups use Genlock cables (analog video sync) or PTP (Precision Time Protocol, IEEE 1588) for hard-real-time alignment. For most installation art, UDP + NTP is good enough.
</Admonition>

**Reflection questions**

- Why is the controller-renderer separation important even for a 2-machine setup?
- The diagram shows "Skew: 8 ms." What does that translate to in terms of visible alignment error on a 60 Hz display?
- What happens if the controller crashes?

<Dropdown summary="Answers">

**Two-machine separation** — even with two machines, the same Python code runs on both. The controller computes state; renderer A draws the left half; renderer B draws the right half. Doubles the resolution without doubling the complexity. If you tried to centralise both rendering and global state on one machine, you'd be limited by that machine's GPU.

**8 ms skew** — at 60 Hz each frame is 16.7 ms long. An 8 ms skew is half a frame — the renderers may be one frame off from each other temporarily. For most content this is invisible; for fast-scrolling text or strobe effects it's visible. Add a frame-buffer queue + time-coded sync to eliminate it.

**Controller crash** — renderers stop receiving updates; they freeze on the last frame. Production setups have a **failover controller** that takes over within 100 ms; the renderers detect missing packets and switch to the backup automatically.

</Dropdown>

</Exercise>

<Exercise n={2} kicker="MODIFY" title="Sweep the rig parameters">

**Goals**

1. **More renderers.** Increase `N_RENDER` from 4 to 8. The diagram becomes denser.
2. **Slower sync.** Reduce the packet rate visually. Useful for low-budget setups where you can't afford 60 Hz.
3. **Multicast.** Replace the broadcast address with a multicast address (`224.0.0.1`). Same effect; allows multiple controllers to coexist on the same LAN without packet floods.

<Dropdown summary="Goal 1 — what to expect">

Eight renderers, eight links from the controller. Visually busier; matches a real concert rig that drives 8 projection surfaces.

</Dropdown>

<Dropdown summary="Goal 2 — what to expect">

Slower packet animation. In a real system, 30 Hz sync is fine for most content; only fast-moving content needs 60 Hz.

</Dropdown>

<Dropdown summary="Goal 3 — what to expect">

Multicast lets the controller send one packet that all subscribed receivers get. Reduces broadcast pollution on busy networks. Operationally identical to broadcast for this use case.

</Dropdown>

#### Make it your own

- **Add Pillow rendering.** Each renderer draws to a PIL Image based on the received frame number; saves as PNG to a frames directory; you stitch the frames offline.
- **Frame-locked PTP.** Set up `ptpd` on all machines to share a clock with sub-millisecond accuracy. Now your renderers can synchronise to within a few µs.
- **Failover controller.** Run two controllers; have renderers detect when one stops sending and switch to the other. The basis of high-availability stage rigs.

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

Multi-machine setups split rendering across multiple GPUs: one controller broadcasts global state; N renderers each draw their assigned slice. UDP is the right transport (low latency, no connection state); TCP is reserved for content delivery. Clock skew is unavoidable; time-coded sync lets renderers align to a shared wall-clock. NTP/PTP align the clocks themselves. Same architectural pattern as DMX, Art-Net, sACN, NDI, and every other "one source of truth, many receivers" protocol. Production setups add failover controllers and frame-locking for hard-real-time alignment.

</Admonition>

**Common pitfalls to avoid**

- **TCP for sync.** Retransmits arrive too late to be useful; lost packets should be dropped, not resent.
- **Forgetting clock sync.** Two machines without NTP can have multi-second clock skew, making time-coded sync useless.
- **Per-renderer code.** If renderers run different code, divergence is inevitable. One renderer codebase, parameterised by index.
- **No failover.** Single-controller setups have a single point of failure. Production setups have hot backups.
