## Big Question — *how do you let someone control your TD project without editing the network?* <a id="big-question"></a>

In a development environment you click directly on operator parameters to adjust them. In a finished installation or live performance there should be no operator parameters visible — the user sees a clean control surface with named knobs and buttons. TouchDesigner builds these surfaces with the same node paradigm as the rest of the system: **Container COMPs** hold **Widget COMPs** (Button COMP, Slider COMP, Field COMP), and each widget exposes its current state through a **Panel CHOP** that you wire into your visual parameters. Building UI this way means the same patterns from 10.3.3 apply: components, custom parameters, reusable layout. The dirty secret is that TD UIs require more thought than you might expect — every text label is a Text TOP, every panel boundary is a positioned Container COMP, and laying out a clean interface takes 20–40 nodes on its own.

### Learning objectives

<ol class="obj-list">
  <li>Build a Container COMP as the top-level UI canvas and arrange Widget COMPs as children inside it.</li>
  <li>Use Button COMP, Slider COMP, and Field COMP for the three most common control types.</li>
  <li>Read widget state through Panel CHOPs and wire those channels into visual parameters.</li>
  <li>Lay out widgets with absolute positioning (`tx`, `ty`) or with Layout COMPs for flexible arrangement.</li>
</ol>

## Part 1 — Container COMP as canvas <a id="part-1"></a>

Container COMP is a visible component with width, height, position, and a `Background TOP` slot. Drop one onto your network and a rectangular region appears in the perform-mode view. The Container COMP's `Layout` page lets you set its size (`Width`, `Height`), its anchor (top-left/centre), and its background colour.

Inside the Container, you place Widget COMPs as children. Each widget has its own position relative to the parent. With three buttons stacked vertically you would set:

- Button 1: `tx=10, ty=10, w=80, h=30`
- Button 2: `tx=10, ty=50, w=80, h=30`
- Button 3: `tx=10, ty=90, w=80, h=30`

The whole UI is a tree: top-level Container COMP holds widget Container COMPs, each of which may hold further nested widgets. Modifying a parent's position translates everything inside.

<Admonition type="dyk" title="Did you know? · Same model as web browsers">
The Container + child-widget + relative-positioning model is essentially HTML's box model. TouchDesigner's layout system is simpler than CSS but the mental model transfers: containers nest, children position inside parents, the parent's coordinate system applies to children. If you have written HTML before, this is familiar territory [1].
</Admonition>

## Part 2 — Three core widgets <a id="part-2"></a>

**Button COMP** — a clickable region. Outputs `1` when pressed, `0` otherwise (or toggles, if configured as a toggle button). Reads via `op('button1/panel1').par.state`. Use for: triggers, mode switches, scene changes.

**Slider COMP** — a draggable knob/strip outputting a continuous `[0, 1]` value. Reads via `op('slider1/panel1').par.value`. Use for: brightness, speed, intensity, anything continuous.

**Field COMP** — a text input box. Outputs the typed string. Use for: filenames, captions, OSC addresses.

Each Widget COMP has a **Panel CHOP** inside it (`panel1` by default) whose channels expose the widget's state. To use the widget's output, you wire that Panel CHOP into your visual network:

```
Slider COMP (slider1)
  inside: panel1 channel "value"

Reference from elsewhere:
  op('slider1/panel1')['value']      → the current 0..1 value
  op('slider1/panel1')['u']          → the cursor's x within the widget
  op('slider1/panel1')['v']          → the cursor's y within the widget
```

Wiring a Slider's `value` channel into a Blur TOP's `size` parameter makes the slider control the blur amount in real time.

<Admonition type="important">
Do not put visualisation operators (Noise TOPs, Blur TOPs) inside Widget COMPs. The widget Container has a fixed size; visualisation TOPs cook at *their own* resolution. Keep visual networks in a separate top-level container and reference widget values across the boundary.
</Admonition>

## Part 3 — Layout strategies <a id="part-3"></a>

Two layout approaches, and you will use both:

**Absolute positioning** — set each widget's `tx`, `ty`, `width`, `height` directly. Total control, manual labour. Use for fixed-layout panels where you know every widget's place.

**Layout COMPs** — `Layout COMP` arranges children in a row, column, or grid automatically. Add or remove children and the others reflow. Use for dynamic panels (a preset list, a parameter grid that grows when the artist adds more).

For most projects the right answer is: a Layout COMP for the overall structure (a vertical column of sections), and absolute positioning for the widgets within each section.

A simple control panel skeleton:

```
Container COMP "control_panel" (1000 × 600)
├── Container COMP "section_audio" (1000 × 200, ty=0)
│   ├── Slider COMP "bass" (tx=10, ty=10)
│   ├── Slider COMP "mids" (tx=100, ty=10)
│   └── Slider COMP "treble" (tx=190, ty=10)
├── Container COMP "section_visual" (1000 × 200, ty=200)
│   ├── Slider COMP "brightness" (...)
│   └── Slider COMP "blur" (...)
└── Container COMP "section_presets" (1000 × 200, ty=400)
    └── Button COMP × 8 in a row (...)
```

Once the layout is wired, you reference widget values from visual operators:

```python
op('blur1').par.size.expr = "op('/control_panel/section_visual/blur/panel1')['value'] * 50"
```

<Admonition type="note">
A common architectural pattern: a Base COMP called `ui` holds the entire control panel; a Base COMP called `audio_engine` holds the audio analysis; a Base COMP called `visuals` holds the actual rendering. Cross-component references go through the parent's container so paths stay stable. This is essentially MVC for TD.
</Admonition>

## Synthesis project — a 3-section control panel <a id="synthesis"></a>

Build a UI panel with three labelled sections: Audio (3 sliders), Visual (3 sliders), Presets (4 buttons). Wire each slider's value into a corresponding parameter in a visual network. Wire each button to a Script DAT that snaps the slider values to a preset configuration.

**Reflection questions**

- A Widget COMP has its own Panel CHOP. Why is the state on the Panel CHOP rather than directly on the COMP?
- You want to label every slider with the parameter name it controls. What is the cleanest way to do that?
- The same UI works in both edit mode (with operator panels visible) and perform mode (full-screen UI only). What is the difference between the two modes?

<Dropdown summary="Answers">

**Panel CHOP separation** — keeping the state on a Panel CHOP makes it accessible like any other CHOP. You can filter it with a Filter CHOP, mix it with other channels, save its history with Trail CHOP. If state were a property of the COMP itself, you would need special accessor methods. The CHOP abstraction unifies UI state with all other channel data.

**Labelling sliders** — add a `Text TOP` inside each Slider's Container COMP, positioned above or below the slider's draggable area. The Text TOP renders the label as part of the widget's visual. Alternatively, use `Slider COMP`'s built-in `Title` parameter if you only need a short label.

**Edit vs perform mode** — edit mode shows the network and operator parameters; perform mode (`F1`) shows only the top-level Container COMP rendered full-screen. Same project, different presentation. Perform mode is what your audience sees.

</Dropdown>

#### Make it your own

- **Build a custom widget**: a circular knob (Container COMP with a Circle TOP, mouse position drives the rotation, output the rotation as a Panel CHOP channel). Encapsulate as a reusable `.tox`.
- **Theme**: make a `theme` Base COMP that exposes colour custom parameters (background, foreground, accent). Every UI widget references the theme parameters. Change the theme and the entire UI repaints.
- **Save UI state to disk**: a Script DAT that walks every widget, reads its current value, writes the lot to a JSON file. Reload restores the state. The pattern foreshadows the preset system in lesson 10.4.3.

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

UIs in TouchDesigner are built from Container COMPs and Widget COMPs (Button, Slider, Field). Widget state lives on a Panel CHOP inside the widget; reference that CHOP's channels from your visual operators to make controls drive visuals. Layout is either absolute positioning or Layout COMP-based flow. The same patterns from custom Components (10.3.3) apply: encapsulate, expose, reuse. Architecturally, separate UI from visuals into different top-level Containers so each can evolve independently.

</Admonition>

**Common pitfalls to avoid**

- Putting heavy visualisation operators inside widget Containers. They cook at the widget's resolution and look wrong.
- Hard-coding widget positions in pixel coordinates that break at different output resolutions. Use percentages or anchored layouts.
- Forgetting to wire widget output into visual parameters. The slider moves, nothing happens — you forgot the expression.
- Reading widget state via DAT cells instead of Panel CHOPs. Panel CHOPs are the canonical interface.
- Building a UI without a theme. Changing colours later means editing every widget by hand.
