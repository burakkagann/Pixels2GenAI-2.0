## Overview <a id="overview"></a>

WebSocket (RFC 6455, 2011) and WebRTC (W3C standard, 2017) are the two protocols that brought real-time interactivity to the browser. Before them, browsers could only do HTTP request/response — every "live update" required polling the server every few seconds. After them, browsers can hold open connections and stream audio/video peer-to-peer with sub-100 ms latency.

- **WebSocket** — a persistent TCP connection that both sides can send messages over at any time. Replaces HTTP polling for chat, collaborative editing, dashboards, multiplayer games, and IoT control surfaces. Library support: `websockets` (Python), `socket.io` (Node), built into every browser.
- **WebRTC** — peer-to-peer audio, video, and data channels with browser-native NAT traversal. Powers Google Meet, Zoom, Discord audio, every Twitter Spaces, every clubhouse-clone. Library support: `aiortc` (Python), browser-native.

This lesson is the protocol-comparison overview. The next lesson (11.4.3) builds an actual remote-control UI in HTML + WebSocket Python backend.

## Quick start — three protocols at a glance <a id="quick-start"></a>

<CodeBlock lang="python" file="quick_start.py">
```python
# WebSocket server (Python)
import asyncio, websockets

async def handler(ws):
    async for message in ws:
        await ws.send(f'echo: {message}')

async def main():
    async with websockets.serve(handler, 'localhost', 8765):
        await asyncio.Future()  # run forever

asyncio.run(main())
```

## Core concepts <a id="core-concepts"></a>

### Concept 1 — HTTP polling vs. WebSocket

**HTTP polling** is the pre-WebSocket workaround for real-time updates: the client sends a GET request every N seconds; the server responds with the current state. For a 1-second polling interval, the average update latency is 500 ms, the worst-case is 1 s. Each request opens a new TCP connection, sends headers, waits, receives headers + body, closes. The per-update overhead is ~1 KB of HTTP headers, even for a 10-byte status update.

**WebSocket** opens *one* TCP connection at the start, upgrades it from HTTP to the WebSocket protocol, and then both sides can send messages whenever they want. The per-message overhead is 2–14 bytes — negligible compared to the message payload. Latency is bounded by network RTT (~10 ms on LAN, ~50 ms across the Atlantic). The connection stays open until either side explicitly closes it.

<CodeBlock lang="python" file="websocket_server.py">
```python
import asyncio, websockets, json, time

clients = set()

async def handler(ws):
    clients.add(ws)
    try:
        async for raw in ws:
            data = json.loads(raw)
            # Broadcast to all clients
            for c in clients:
                await c.send(json.dumps({'t': time.time(), **data}))
    finally:
        clients.discard(ws)

async def main():
    async with websockets.serve(handler, '0.0.0.0', 8765):
        await asyncio.Future()

asyncio.run(main())
```
</CodeBlock>

### Concept 2 — WebRTC: signalling + media

WebRTC is **fundamentally peer-to-peer**. The browser opens a direct UDP/RTP connection between the two participants — neither side's media goes through a server. Pros: low latency (often 50 ms even across continents), no server bandwidth bills. Cons: requires NAT traversal (most home routers don't expose direct UDP) via STUN/TURN servers, and requires a **signalling channel** for the two peers to exchange connection metadata.

The signalling is usually done over WebSocket: the two clients exchange "I'm at this IP:port, I support these codecs, here's my session description" messages. Once signalling completes, the media bypasses the signalling server entirely — direct P2P.

<Admonition type="dyk" title="Did you know · Google open-sourced WebRTC in 2011">
WebRTC's reference implementation is `libwebrtc`, the same C++ codebase Google uses in Chrome, Hangouts, Meet, and most of their video products. Mozilla and Apple ship it (modified) in Firefox and Safari [1]. The implementation is over 1 million lines of C++ and is one of the most complex pieces of code in any browser. As a developer, you interact with a small subset of the JavaScript API (`RTCPeerConnection`, `getUserMedia`); the C++ machinery handles audio capture, video encoding, RTP packetization, jitter buffering, and NAT traversal.
</Admonition>

### Concept 3 — Matching protocol to use case

A short matrix:

| Use case | Protocol | Why |
|----------|----------|-----|
| Server status indicator (refresh every 30 s) | HTTP polling | Simple, no persistent state |
| Live chat / collaborative editor / dashboard | WebSocket | Bi-directional, low latency, low overhead |
| Video conference / live stream | WebRTC | Native audio/video codecs, P2P bandwidth |
| Multiplayer game state sync | WebSocket | Reliable ordered messages at 30+ Hz |
| File upload progress | HTTP polling or SSE | One-way push from server is sufficient |
| MIDI controller over the network | WebSocket | Sub-frame latency for instrument-like response |
| Streaming a generative-art frame to remote viewers | WebRTC | Browser-native video encoding/decoding |

Pick the protocol by what you need to move: **state** (WebSocket), **media** (WebRTC), or **occasional checks** (HTTP polling).

<Admonition type="important">
**Server-Sent Events** (SSE) is a fourth option not covered here in detail: a one-way persistent connection from server to client over HTTP. Lighter weight than WebSocket if you only need server→client push (no client→server messages). Used by Stripe webhooks, GitHub event streams, and most "live progress bar" implementations [2].
</Admonition>

**Reflection questions**

- The HTTP polling row shows large packets at long intervals. What's in those packets that makes them larger than WebSocket's?
- The WebRTC row shows two parallel media channels. What are they?
- Why is the WebRTC server label noted as "signalling only"?

<Dropdown summary="Answers">

**HTTP packet size** — HTTP headers. Even a 10-byte status query carries ~1 KB of `User-Agent`, `Accept`, `Cookie`, `Authorization`, etc. WebSocket frames drop the headers after the initial handshake.

**WebRTC dual channels** — audio and video. Each is a separate RTP stream with its own packetization and codec. WebRTC also supports a separate `RTCDataChannel` for arbitrary binary messages, but our visualisation shows the canonical audio+video case.

**Signalling-only server** — once the two browsers exchange session descriptions (SDP) and ICE candidates via the signalling server, the media flows directly between them. The server's bandwidth bill is bounded by the handshake size (a few KB) regardless of how long the call lasts. This is what makes WebRTC economical for large-scale video products.

</Dropdown>

#### Make it your own

- **Broadcast.** Maintain a set of all connected clients. Each new message gets relayed to every client. The basis of every chat room.
- **Authentication.** Require a JWT or signed token in the first message. Reject unauthenticated connections.
- **WebRTC data channel.** Replace the WebSocket transport with an `RTCDataChannel`. Same API, but P2P (no server in the message path).

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

HTTP polling = burst request/response (high latency, simple). WebSocket = persistent bidirectional TCP (low latency, low overhead, the standard for chat / dashboards / controllers). WebRTC = P2P audio/video/data with browser-native NAT traversal (the only viable option for video calls). The Python `websockets` library makes a WebSocket server a 10-line program. WebRTC requires a signalling server (often WebSocket-based) for connection setup; once established, media flows P2P. Pick the protocol by what you need to move — state for WebSocket, media for WebRTC, occasional polls for HTTP.

</Admonition>

**Common pitfalls to avoid**

- **Using HTTP polling for real-time.** Latency too high, overhead too large. Always upgrade to WebSocket.
- **Sending huge JSON payloads over WebSocket.** Use binary frames + MessagePack/Protobuf for performance-critical data.
- **No reconnect logic on client.** Connections drop in the real world; clients should retry with exponential backoff.
- **Treating WebRTC as a server-pull architecture.** WebRTC media flows P2P; only signalling goes through the server.
