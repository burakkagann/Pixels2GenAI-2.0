## Overview <a id="overview"></a>

Swap the webcam for a microphone and the pipeline is identical: capture a buffer, transform it, display the result. The buffer is now a 1D `float32` array of audio samples instead of a 2D `uint8` array of pixels. The transformation is a **Fast Fourier Transform** (FFT) that decomposes the waveform into a frequency spectrum. The display is whatever visualization you built in 8.4.1 — bars, particles, fractal-zoom parameters, any quantity that benefits from being modulated by sound.

This lesson uses synthesised audio (no PyAudio dependency required) so the pipeline runs on any machine. The same code drives a live mic input with one swap: replace `synth_audio(...)` with `pyaudio.Stream.read(...)`. Everything downstream stays the same.

### Learning objectives

<ol class="obj-list">
  <li>Window an audio buffer and compute its short-time FFT magnitude spectrum.</li>
  <li>Compress the FFT bins logarithmically — human hearing is log-frequency, so bins should be too.</li>
  <li>Smooth the spectrum over time with exponential smoothing so the visualizer doesn't jitter.</li>
  <li>Drive a visualization (bars + pulse) from the bins with VU-meter colour conventions.</li>
</ol>

## Quick start — audio-reactive visualizer <a id="quick-start"></a>

<CodeBlock lang="python" file="quick_start.py">
```python
import numpy as np
from PIL import Image, ImageDraw

def spectrum(window, n_bins=32):
    fft = np.abs(np.fft.rfft(window * np.hanning(len(window))))
    n = len(fft)
    edges = np.logspace(np.log10(1), np.log10(n - 1), n_bins + 1).astype(int)
    bins = np.array([fft[edges[i]:edges[i+1]+1].mean() for i in range(n_bins)])
    return bins / (bins.max() + 1e-9)

# Drive the renderer with the smoothed spectrum each frame
smoothed = None
for window in audio_windows:
    s = spectrum(window)
    smoothed = s if smoothed is None else 0.6 * s + 0.4 * smoothed
    render_frame(smoothed).save(f'frame_{i:03d}.png')
```
</CodeBlock>

## Core concepts <a id="core-concepts"></a>

### Concept 1 — Windowing and the short-time FFT

A single FFT on the whole signal gives one global spectrum — useless for real-time visuals. Instead, take **short windows** of the signal (typically 1024 or 2048 samples ≈ 23–46 ms at 44.1 kHz) and FFT each window independently. The result is a **time-varying spectrum**, one per visualization frame.

Multiplying the window by a smooth taper (`np.hanning(N)`) before the FFT suppresses **spectral leakage** — the false high-frequency content that an abrupt window edge would create. Hanning, Hamming, and Blackman windows all do this; Hanning is the cheap default [1].

<CodeBlock lang="python" file="windowed_fft.py">
```python
window = audio[start:start + WINDOW_SIZE]
spectrum = np.abs(np.fft.rfft(window * np.hanning(WINDOW_SIZE)))
```
</CodeBlock>

`rfft` is the real-input variant of `fft` — half the output bins, twice as fast. The output is complex; `np.abs` gives the magnitude.

### Concept 2 — Log-spaced binning

A 1024-sample FFT at 22050 Hz gives bins every ~22 Hz. Linear: bin 1 is 22 Hz; bin 100 is 2200 Hz; bin 500 is 11000 Hz. The problem: **human hearing is logarithmic**, not linear. The musical octave from 110 to 220 Hz uses 5 bins; the octave from 880 to 1760 Hz uses 40 bins. Visualizing them linearly wastes screen on the treble end and starves the bass.

The fix: average linear bins into **log-spaced** bins:

<CodeBlock lang="python" file="log_bins.py">
```python
log_edges = np.logspace(np.log10(1), np.log10(n_lin_bins - 1),
                        n_log_bins + 1).astype(int)
bins = np.array([fft[log_edges[i]:log_edges[i+1]+1].mean()
                 for i in range(n_log_bins)])
```
</CodeBlock>

32 log-bins spans the audible range with roughly equal perceptual weight per bin. Bass bins are wider (each averages more FFT cells); treble bins are narrower. This is why every music visualizer you've ever seen — Winamp, iTunes, Spotify — uses log spacing.

<Admonition type="dyk" title="Did you know · mel and bark scales go further">
For speech and music applications that need *perceptually-uniform* frequency spacing, the **mel scale** [2] (used in audio ML, including all of OpenAI's Whisper and Audio2Music models) and the **Bark scale** [3] (used in psychoacoustic compression like MP3 and AAC) refine the log idea with empirical corrections derived from listening tests. For visualization purposes, plain `logspace` is sufficient and runs faster.
</Admonition>

### Concept 3 — Exponential smoothing for visual stability

A raw spectrum jitters frame-to-frame because FFT magnitudes have stochastic variation. Visualizing it directly produces a flickering, hard-to-read display. The fix is **exponential smoothing**: blend the new spectrum with the previous frame's smoothed values:

<CodeBlock lang="python" file="smoothing.py">
```python
alpha = 0.6   # new-frame weight; lower = smoother
smoothed = alpha * new_bins + (1 - alpha) * smoothed_prev
```
</CodeBlock>

`alpha = 1` is no smoothing (full jitter). `alpha = 0.3` is very smooth but laggy. `alpha = 0.6` is the sweet spot for most music visualizers: responsive to beats, still steady to look at. The same primitive (IIR low-pass filter) drives the level meters on every DAW and the bass-bins of every audio-reactive DJ visualization [4].

<Admonition type="important">
The smoothing should be **per-bin**. Smoothing the *overall amplitude* and using that to scale all bars uniformly destroys the spectrum structure — drums and bass pulses would no longer be readable. Smooth each bin independently with the same `alpha`.
</Admonition>

<Exercise n={1} kicker="EXECUTE" title="Run the audio visualizer">

Run `audio_reactivity.py`. The script synthesises a 3-second drum loop and renders 90 frames.

<Download href="/lesson-media/Module_11_interactive_systems/11.1_input_devices/11.1.2_audio_reactivity/audio_reactivity.py" label="audio_reactivity.py — synthetic-audio reference" />

**Reflection questions**

- The kick drum is at 60 Hz. Which bin in a 32-log-bin spectrum should respond to it?
- The script uses `np.hanning`. What does the spectrum look like if you skip the window taper?
- The smoothing factor is `alpha = 0.6`. What does `alpha = 1.0` look like? `alpha = 0.2`?

<Dropdown summary="Answers">

**Kick bin** — log-spaced bins from ~22 Hz to ~11 kHz over 32 buckets place 60 Hz in roughly bin 2 (the first bin covers 22–60 Hz, the second covers 60–105 Hz). Watch the leftmost few bars during the kick beats — they should flash brightest.

**No window** — the spectrum gets noisy edges from spectral leakage; bins between active frequencies show up as low-level "smear." On a clean monotone you'd see a sharp peak with `np.hanning` and a smear with the bare rectangular window.

**`alpha` extremes** — `1.0` is no smoothing (jitter, harsh); `0.2` is heavy smoothing (delayed response, soft). `0.6` is responsive enough to feel beat-tight but smooth enough to read.

</Dropdown>

</Exercise>

<Exercise n={2} kicker="MODIFY" title="Sweep visualization parameters">

**Goals**

1. **More bins.** Increase `N_BINS` from 32 to 64. The visualizer has finer pitch resolution but each bar is narrower.
2. **Slower smoothing.** Lower `alpha` to 0.3. The visualizer feels weighty.
3. **Different audio.** Replace the synthesized loop with `np.sin(2 * np.pi * 440 * t)` — a pure 440 Hz sine. Watch which bin lights up.

<Dropdown summary="Goal 1 — what to expect">

64 narrower bars with more pitch detail. Better for resolving multiple simultaneous instruments; worse if you want a chunky retro look.

</Dropdown>

<Dropdown summary="Goal 2 — what to expect">

The visualizer responds to beats more slowly — bars rise and fall gradually rather than snapping with each hit. Use for ambient/orchestral content; bad for fast electronic music.

</Dropdown>

<Dropdown summary="Goal 3 — what to expect">

A single bin at ~440 Hz lights up consistently — log-spacing 32 bins from 22 Hz to 11025 Hz puts 440 Hz somewhere around bin 13. The rest of the visualizer stays dark.

</Dropdown>

</Exercise>

<Exercise n={3} kicker="CREATE" title="Add beat detection">

Detect "beats" by watching for **sudden spikes** in the bass band. When the current frame's bass sum exceeds a moving average by some factor, flash the centre disc.

<CodeBlock lang="python" file="exercise3_starter.py">
```python
# Per-frame:
bass = bins[:6].sum()
# TODO 1: maintain a rolling average of bass over the last N frames
# TODO 2: if bass > 1.4 * rolling_avg, set beat_flash = 1
# TODO 3: each frame, beat_flash *= 0.85 (decays)
# TODO 4: scale the centre disc's brightness by 1 + beat_flash
```
</CodeBlock>

<Dropdown summary="Hint 1 — rolling average">

```python
bass_history = []          # outside the loop
# Inside the loop:
bass = bins[:6].sum()
bass_history.append(bass)
if len(bass_history) > 30:
    bass_history.pop(0)
rolling_avg = sum(bass_history) / len(bass_history)
```

30 frames at 30 fps = 1 second average. Long enough to be stable, short enough to track tempo changes.

</Dropdown>

<Dropdown summary="Hint 2 — beat flash decay">

```python
if bass > 1.4 * rolling_avg:
    beat_flash = 1.0
else:
    beat_flash *= 0.85
disc_brightness = 1 + beat_flash    # 1 normally, up to 2 on beat
```

The `* 0.85` per frame produces a clean exponential decay over ~12 frames.

</Dropdown>

<Dropdown summary="Complete solution">

Combined with the existing centre disc, every kick lights it up brighter for ~400 ms. Same primitive drives every "DJ light-show" on every clip-show post.

</Dropdown>

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

Audio reactivity is the same capture-process-display loop as the webcam, with audio buffers and FFTs instead of frames and image filters. Windowing prevents spectral leakage; log-spaced bins match human hearing; exponential smoothing produces stable visuals. Any 8.4.1-style visualizer can be driven by these bins. Beat detection adds another expressive layer — a band's energy spike triggers a per-event animation. Replace the synthesised audio with a real mic input and the rest of the pipeline doesn't change.

</Admonition>

**Common pitfalls to avoid**

- **Skipping windowing.** Sharp edges produce spectral leakage. Always taper.
- **Linear binning.** Hides bass detail under a wall of treble bins. Always log-space.
- **Per-frame jitter without smoothing.** Visualizer flickers; viewers tire.
- **Buffer size mismatch.** The audio frame rate (samples/sec) must align with the display rate. Drop or interpolate buffers if they diverge.
