## Overview <a id="overview"></a>

A **depth-sensor camera** measures the distance from the camera to every pixel in the scene. Microsoft's first-generation Kinect (2010) used a projected infrared dot pattern and structured-light triangulation; the Kinect 2 (2014) and Azure Kinect (2019) switched to time-of-flight measurement. Leap Motion (2013) used two infrared cameras and stereo vision optimised for hand poses at desk distance. Modern smartphones (iPhone Pro, Pixel Pro) use LiDAR with similar accuracy [1].

The output is a depth map: a 2D array where each pixel value is millimetres-from-camera instead of brightness. From the depth map, a pose-estimation network reconstructs a **skeleton** — a set of 3D joint positions (head, neck, shoulders, hands, hips, knees, feet) at 30+ Hz. The skeleton is what drives gesture-based interaction: wave detection, hand tracking for VR, full-body controllers for installation art.

This lesson uses a synthesized depth map and skeleton so you can build the visualization pipeline without owning a depth sensor.

## Quick start — depth map + skeleton overlay <a id="quick-start"></a>

<CodeBlock lang="python" file="quick_start.py">
```python
import numpy as np
from PIL import Image, ImageDraw

# depth: HxW uint8, higher value = closer to camera
# skeleton: dict of joint_name -> (x, y)

def render(depth, skeleton):
    H, W = depth.shape
    img = np.zeros((H, W, 3), dtype=np.uint8)
    norm = depth.astype(np.float32) / 255
    img[..., 0] = (30 + 220 * norm).clip(0, 255).astype(np.uint8)
    img[..., 1] = (70 + 100 * norm).clip(0, 255).astype(np.uint8)
    img[..., 2] = (120 + 60 * (1 - norm)).clip(0, 255).astype(np.uint8)

    pil = Image.fromarray(img)
    draw = ImageDraw.Draw(pil)
    for a, b in [('head','neck'),('neck','torso'),('neck','left_hand'),('neck','right_hand')]:
        draw.line([skeleton[a], skeleton[b]], fill=(255, 255, 110), width=3)
    return pil
```
</CodeBlock>

## Core concepts <a id="core-concepts"></a>

### Concept 1 — Depth map = 2D distance array

The depth map's shape is `(H, W)`, single-channel, but the semantics differ from a grayscale image: each pixel value is **a measured distance** rather than a measured brightness. Common encodings:

- **16-bit millimetres** — raw sensor output, e.g. `5210` = 5.21 metres. Range: typically 500–4500 mm for Kinect-class sensors.
- **8-bit normalised** — quantized to 0–255, often with `0 = invalid` (no return signal). Used for visualization.
- **Float metres** — normalised to physical units, used in robotics.

The most useful operations on a depth map are **thresholding** (extract pixels within a depth band, e.g. 1–2 m from camera) and **normal estimation** (compute the surface normal at each pixel — useful for lighting computation).

```python
# Threshold: only pixels between 1.0 and 2.0 metres

# Background removal: keep only the foreground subject
```

### Concept 2 — Skeleton from depth

Modern depth sensors ship with a pose-estimation network that consumes the depth map and outputs a **skeleton**: a set of named joints, each with a 3D position. For Kinect Azure it's 32 joints; for Leap Motion it's 27 hand joints. For Apple Vision Pro it's a full upper-body skeleton with hand tracking.

The naming convention varies but the structure is the same: a tree where the root is `pelvis` (or `body_centre`), children are limbs, leaves are extremities (`head`, `left_hand`, `right_foot`).

<CodeBlock lang="python" file="skeleton_render.py">
```python
def draw_skeleton(draw, joints):
    bones = [
        ('head', 'neck'), ('neck', 'torso'), ('torso', 'pelvis'),
        ('neck', 'left_shoulder'), ('left_shoulder', 'left_hand'),
        ('neck', 'right_shoulder'), ('right_shoulder', 'right_hand'),
        ('pelvis', 'left_knee'), ('left_knee', 'left_foot'),
        ('pelvis', 'right_knee'), ('right_knee', 'right_foot'),
    ]
    for a, b in bones:
        draw.line([joints[a], joints[b]], fill=(255, 255, 110), width=3)
    for x, y in joints.values():
        draw.ellipse([x - 5, y - 5, x + 5, y + 5], fill=(255, 230, 110))
```
</CodeBlock>

The skeleton is the data structure your gesture-recognition code actually consumes. The depth map is *consumed by* the network; the skeleton is *produced by* the network.

<Admonition type="dyk" title="Did you know · the original Kinect was hacked open in days">
Microsoft released Kinect for Xbox 360 in November 2010 as a closed peripheral. Within 6 days, Adafruit Industries paid a $3000 bounty to the first open-source driver, won by Héctor Martín [2]. Within weeks the open-source `libfreenect` driver was reading depth maps on Linux, Mac, and Windows. Within months the *Kinect Hacks* community had wired Kinects into Processing, openFrameworks, Cinder, and TouchDesigner. Microsoft eventually leaned into it, releasing the official Kinect SDK in 2012. The whole interactive-art world adopted the device in months because the cost ($150) was unprecedented for a depth-sensing device.
</Admonition>

### Concept 3 — Gesture recognition from joint motion

Once you have a skeleton at 30 fps, **gestures** are time-derivative features of joint motion:

- **Wave** — `right_hand.x` oscillates with period 0.5–1 s; `right_hand.y > shoulder.y`.
- **Jump** — `pelvis.y` decreases (camera-down direction) faster than gravity, then rebounds.
- **T-pose** — both hands at shoulder height; absolute angle between arms is approximately 180°.
- **Grab** — distance between thumb-tip and index-tip drops below a threshold (Leap Motion only — Kinect doesn't have finger-level detail).

These rules can be implemented as plain Python conditions. For more sophisticated recognition, train an LSTM on labelled joint sequences (Module 9.2 covers RNN architectures).

<Admonition type="important">
Skeleton positions are **noisy**. Frame-to-frame, a stationary hand jitters by a few centimetres because of sensor noise and pose-network uncertainty. Always smooth joint positions with exponential smoothing (the same primitive as 11.1.2's audio smoothing) before computing gestures. `alpha = 0.3` is a good default.
</Admonition>

**Reflection questions**

- The depth map uses 8-bit values. What's the practical implication for distinguishing objects at 2.5 m vs 2.6 m?
- The skeleton's joint positions come from a `synth_depth_to_skeleton` function. What does a real Kinect SDK do at this step?
- Why is the torso the warmest colour in the depth map?

<Dropdown summary="Answers">

**8-bit precision** — 256 levels across the sensor's depth range (say 500–4500 mm = 4 m). Each level represents ~16 mm. Objects at 2500 and 2516 mm read identical. Real applications use 16-bit depth (65536 levels = sub-millimetre precision).

**Real pose estimation** — runs a CNN trained on synthetic + labelled real depth data. Microsoft's Kinect for Xbox One used a 4-layer CNN with random-forest refinement [3]; modern Apple/Google solutions use transformer-based pose networks with full-body and hand sub-models. The architecture is opaque to the application code — you only see the joint output.

**Warmest torso** — by convention, "close" = warm (high R, low B) and "far" = cool (low R, high B). The torso is the *closest* part of the body to the camera; assigning it warm orange makes it stand out as the foreground subject.

</Dropdown>

</Exercise>

<Exercise n={2} kicker="MODIFY" title="Sweep visualization parameters">

**Goals**

1. **Different palette.** Replace the warm/cool palette with a black-to-white grayscale ramp. The depth map will look like a traditional Z-buffer.
2. **Depth threshold.** Set all pixels with `depth < 100` (far background) to pure black. The subject "pops" from the background.
3. **Joints only.** Skip the bones — render only the joint dots. The skeleton becomes a constellation of points.

<Dropdown summary="Goal 1 — what to expect">

Looks like a 3D engine's depth buffer. Useful for technical debugging; less readable than a coloured palette for art applications.

</Dropdown>

<Dropdown summary="Goal 2 — what to expect">

A floating figure on a black background — exactly the "person against a void" look used in interactive installations. The technique is called **depth-keyed background removal** and is the depth equivalent of green-screen chroma keying.

</Dropdown>

<Dropdown summary="Goal 3 — what to expect">

A spider-like constellation of yellow dots. Useful for emphasising joint *position* over body *shape* — you can see how the joints relate to each other without the visual clutter of bones.

</Dropdown>

</Exercise>

<Dropdown summary="Hint 1 — height check">

```python
right_x = np.array([s['right_hand'][0] for s in window])
right_y = np.array([s['right_hand'][1] for s in window])
shoulder_y = np.array([s['neck'][1] for s in window])  # using neck as proxy
if not np.all(right_y < shoulder_y):
    return False
```

In screen coordinates, `right_y < shoulder_y` means the hand is *above* the shoulder. (Smaller y = higher on screen.)

</Dropdown>

<Dropdown summary="Hint 2 — zero crossings">

```python
centred = right_x - right_x.mean()
signs = np.sign(centred)
zero_crossings = np.sum(np.diff(signs) != 0)
return zero_crossings >= 4
```

A wave produces a sinusoidal x-position; the centred signal crosses zero twice per oscillation. 4 crossings = 2 oscillations = a clear wave.

</Dropdown>

<Dropdown summary="Complete solution">

```python
def detect_wave(history, fps=30):
    window = history[-int(2 * fps):]
    if len(window) < int(1.5 * fps):
        return False
    right_y = np.array([s['right_hand'][1] for s in window])
    shoulder_y = np.array([s['neck'][1] for s in window])
    if not np.all(right_y < shoulder_y):
        return False
    right_x = np.array([s['right_hand'][0] for s in window])
    centred = right_x - right_x.mean()
    zero_crossings = np.sum(np.diff(np.sign(centred)) != 0)
    return zero_crossings >= 4
```

Combined with a buffer of recent skeletons, this is a working wave detector. Same pattern handles jump, T-pose, and other gestures.

</Dropdown>

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

Depth-sensor cameras produce a per-pixel distance array. The on-device pose-estimation network converts depth into a skeleton: a set of named 3D joint positions. Visualize depth with a warm-close / cool-far palette; visualize the skeleton as a stick figure on top. Smooth joint positions with exponential smoothing before computing gestures — raw skeletons are noisy. The depth + skeleton interface is universal across Kinect, Leap Motion, MediaPipe, Apple Vision Pro, and modern smartphones with LiDAR. Replace one hardware library with another and the visualization, gesture code, and downstream logic all stay put.

</Admonition>

**Common pitfalls to avoid**

- **Treating depth as brightness.** Bright depth pixels are *close*, not *bright*. Render with a depth-aware palette.
- **Reading raw skeleton positions in gesture code.** Sensor noise produces false-positive triggers. Always smooth first.
- **Hard-coded depth thresholds.** A 2 m threshold that works at home may not work in a gallery. Use a calibration step.
- **Missing the coordinate convention.** Some SDKs return depth in millimetres, others in metres; some y-axes point down, others up. Read the docs.
