## Overview <a id="overview"></a>

MIDI (Musical Instrument Digital Interface, 1983) and OSC (Open Sound Control, 1997) are the two dominant control protocols for live performance. MIDI is a serial-byte protocol designed for 1980s synthesizer hardware: every message is a few bytes (note number, velocity, controller value). OSC is a UDP-based protocol designed for modern networked installations: every message is a hierarchical address (`/lights/stage/main`) plus typed arguments (floats, ints, strings).

Both protocols share the same interactive-systems pipeline as the webcam (11.1.1) and microphone (11.1.2): events come in, your handler dispatches them, your visualizer reads the resulting state. The "events come in" differs — `mido` for MIDI, `python-osc` for OSC — but the dispatcher and visualizer are identical.

This lesson uses synthesized events (no hardware required) to focus on the *handler architecture* and visualization. Connecting a real MIDI controller or OSC sender is a one-import swap.

### Learning objectives

<ol class="obj-list">
  <li>Recognise the MIDI byte structure (status byte + 1–2 data bytes) and the OSC packet structure (address + args).</li>
  <li>Build a state table indexed by note number / CC number; update on each incoming message.</li>
  <li>Render a "control surface" dashboard: piano-roll for notes + rotary knobs for CCs.</li>
  <li>Recognise that MIDI and OSC are interchangeable for visualization — only the byte format differs.</li>
</ol>

## Core concepts <a id="core-concepts"></a>

### Concept 1 — MIDI byte structure

A MIDI message has a 1-byte **status** and 1 or 2 bytes of **data**:

- **Note On** (`0x90 + channel`, note, velocity) — note number 0–127 (60 = middle C), velocity 0–127 (1–127 = on; 0 = note-off shorthand).
- **Note Off** (`0x80 + channel`, note, velocity) — release a held note.
- **Control Change / CC** (`0xB0 + channel`, controller, value) — a knob or slider, controller 0–127, value 0–127.
- **Program Change** (`0xC0 + channel`, program) — switch preset.

Channels are 0–15 (16 total). The protocol is **deterministic** — every byte means exactly one thing depending on its position in the message.

<CodeBlock lang="python" file="mido_example.py">
```python
import mido
with mido.open_input() as port:
    for msg in port:
        if msg.type == 'note_on' and msg.velocity > 0:
            notes[msg.note] = msg.velocity / 127.0
        elif msg.type == 'note_off' or msg.velocity == 0:
            notes[msg.note] = 0
        elif msg.type == 'control_change':
            knobs[msg.control] = msg.value / 127.0
```
</CodeBlock>

`mido` handles the byte parsing; your handler dispatches by `msg.type`. The state dictionaries `notes` and `knobs` are read by the visualizer.

### Concept 2 — OSC packet structure

OSC ditches the fixed-byte format for a string-addressed protocol:

`/lights/stage/main/intensity` → 0.83 (float)

The address is a Unix-style path; arguments are typed (int, float, string, blob). One packet per message; UDP transport (no connection setup). Compared to MIDI, OSC trades wire efficiency for **hierarchical naming** — an OSC server can route messages by prefix (`/lights/*` to the lighting subsystem, `/lasers/*` to the laser subsystem) instead of by channel number [2].

<CodeBlock lang="python" file="osc_example.py">
```python
from pythonosc.dispatcher import Dispatcher
from pythonosc.osc_server import BlockingOSCUDPServer

def note_handler(addr, note_num, velocity):
    notes[note_num] = velocity

def cc_handler(addr, cc_num, value):
    knobs[cc_num] = value

dispatcher = Dispatcher()
dispatcher.map('/note/*', note_handler)
dispatcher.map('/cc/*', cc_handler)
BlockingOSCUDPServer(('127.0.0.1', 5005), dispatcher).serve_forever()
```
</CodeBlock>

The dispatcher routes by address pattern. Same `notes`/`knobs` state dictionaries; same visualizer below.

<Admonition type="dyk" title="Did you know · TouchDesigner speaks both natively">
TouchDesigner (covered in Modules 10 and 13) has native OPs for both MIDI (`midiinCHOP`, `midioutCHOP`) and OSC (`oscinCHOP`, `oscoutCHOP`). Most production VJ rigs use **MIDI for hardware controllers** (Akai APC, Novation Launchpad) and **OSC for software routing** between TouchDesigner, Ableton Live, Resolume, and custom Python services. The two protocols coexist on every modern stage — pick whichever fits the source [3].
</Admonition>

### Concept 3 — Visualizing the state

The visualizer reads the state dictionaries and renders a control-surface dashboard:

- **Piano roll** — one vertical bar per active note. Bar height = current velocity (decayed since last note-on). Colour can encode pitch, velocity, or channel.
- **Knob row** — one rotary indicator per CC. Pointer angle = value × 270° − 135° (full sweep from -135° to +135°).
- **Label everything** — note number, controller number, current value. Without labels the dashboard is unreadable during live performance.

The render is run from the visualizer thread; the handler runs from the MIDI/OSC input thread. State updates are atomic (Python's GIL makes single-dict assignments thread-safe in CPython), so no explicit locking is needed for this scale.

<Admonition type="important">
The dashboard above is **debugging UI**, not a finished visualization. In production you'd map note velocities and CC values to *visual parameters* — particle counts, colour palettes, fractal zoom rates — not to bars and knobs. The dashboard exists so you can verify your MIDI input is wired up correctly before the show.
</Admonition>

**Reflection questions**

- The notes decay at rate `0.92` per frame. Roughly how many frames does it take a velocity of 1.0 to decay to 0.1?
- The knobs use exponential smoothing toward a target. Why isn't the knob value set instantly?
- What additional MIDI message types would you need to support a full piano keyboard?

<Dropdown summary="Answers">

**Decay length** — `0.92^n = 0.1` gives `n = log(0.1) / log(0.92) ≈ 27.6` frames, or about 920 ms at 30 fps. The decay reads as a natural "envelope" — fast attack, slow release.

**Smoothed knobs** — real hardware knobs send a *continuous* stream of CC values as the user turns the dial. Smoothing the visualizer's display masks per-sample jitter and produces a clean visual sweep even from a noisy input.

**Full keyboard** — at minimum you need Note On, Note Off, and Pitch Bend (for slides). Pedals add Control Change (CC 64 = sustain). Aftertouch (per-key pressure) and Channel Pressure (overall key pressure) add expression. A full piano implementation handles all of these.

</Dropdown>

</Exercise>

<Exercise n={2} kicker="MODIFY" title="Replace MIDI with OSC">

Modify the script to receive events from an OSC server instead of synthesizing them. The address scheme: `/note/{n}` for note velocities, `/cc/{n}` for knob values.

**Goals**

1. **OSC server.** Spin up a `BlockingOSCUDPServer` on port 5005 (run in a background thread).
2. **State dictionaries.** Handlers write to `notes` and `knobs` arrays; the renderer reads them.
3. **Test sender.** Write a small client script that sends events at a fixed rate so you can test without external software.

<Dropdown summary="Goal 1 — server boilerplate">

```python
from pythonosc.dispatcher import Dispatcher
from pythonosc.osc_server import ThreadingOSCUDPServer
import threading

dispatcher = Dispatcher()
dispatcher.map('/note/*', lambda addr, n, v: notes.__setitem__(int(n), v))
dispatcher.map('/cc/*', lambda addr, n, v: knobs.__setitem__(int(n), v))

server = ThreadingOSCUDPServer(('127.0.0.1', 5005), dispatcher)
threading.Thread(target=server.serve_forever, daemon=True).start()
```

`ThreadingOSCUDPServer` lets the renderer keep running while messages arrive.

</Dropdown>

<Dropdown summary="Goal 2 — wire the renderer">

The existing `render_frame` already reads from arrays. No change needed — just point it at the OSC-populated `notes` / `knobs` instead of the synthesized ones.

</Dropdown>

<Dropdown summary="Goal 3 — test sender">

```python
from pythonosc.udp_client import SimpleUDPClient
client = SimpleUDPClient('127.0.0.1', 5005)
for i in range(60):
    client.send_message(f'/note/{i % 8}', 0.8)
    time.sleep(0.1)
```

Run this in a separate terminal while the visualizer is up.

</Dropdown>

</Exercise>

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

MIDI and OSC are the dominant control protocols for live performance. MIDI uses fixed-byte messages over a serial link; OSC uses string-addressed packets over UDP. Both feed the same handler-state-visualizer architecture: incoming messages update a state dictionary; the visualizer reads the dictionary. Swap `mido` for `python-osc` and the rest of the code stays put. The dashboard pattern in this lesson — piano roll for notes + rotary knobs for CCs — is the debugging UI you'll use to verify your input wiring before mapping to real visuals.

</Admonition>

**Common pitfalls to avoid**

- **Blocking handler.** A slow handler stalls the input thread and drops messages. Keep handlers tiny; do the work in the visualizer.
- **No note-off handling.** MIDI uses note-off (or note-on with velocity 0) to end a note. If you only listen to note-on, notes stay "on" forever.
- **OSC server in the main thread.** Blocks the visualizer. Use `ThreadingOSCUDPServer` or run on a separate thread.
- **Channel confusion.** MIDI has 16 channels; not specifying a channel means messages from all channels mix. Filter early.
