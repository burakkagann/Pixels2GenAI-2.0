## Overview <a id="overview"></a>

An Arduino-class microcontroller is a $4 device with 6–10 analog input pins and a USB serial port. Hook up a potentiometer, a photoresistor, an ultrasonic ranger, or any sensor that produces a voltage between 0 and 5 V, and the Arduino sends an integer 0–1023 over USB at ~60 Hz. Your Python script reads the serial line, parses it, and drives whatever visual or effect you want.

This is the **hardware-input** side of every physical-computing installation: a tangible interactive object — a knob someone turns, a wall someone touches, a door that opens — connected to a generative system that responds. Galleries, escape rooms, museum kiosks, theme-park attractions all use the same pattern: Arduino reads physical state, Python or TouchDesigner renders the response.

This lesson uses a synthesized sensor stream so you can build the visualization pipeline without owning an Arduino. The "serial line" is generated by `synth_sensor_packet`; swapping it for `pyserial.Serial(port).readline()` is the only change needed to use real hardware.

### Learning objectives

<ol class="obj-list">
  <li>Recognise the Arduino → USB serial → Python pipeline as event-driven text I/O.</li>
  <li>Parse a serial "packet" — newline-terminated `key:value key:value ...` text — into a Python dict.</li>
  <li>Maintain rolling per-sensor history buffers and render them as oscilloscope-style traces.</li>
  <li>Recognise the same pipeline for other microcontrollers (ESP32, Teensy, Raspberry Pi Pico).</li>
</ol>

## Quick start — sensor dashboard <a id="quick-start"></a>

<CodeBlock lang="python" file="quick_start.py">
```python
import serial
ser = serial.Serial('/dev/ttyACM0', 9600)        # macOS/Linux: cu.usbmodem*; Windows: COM3
while True:
    line = ser.readline().decode('utf-8').strip()
    # Expect "pot:512 lux:80 dist:130"
    data = {p.split(':')[0]: int(p.split(':')[1]) for p in line.split()}
    traces['pot'].append(data['pot'])
    traces['lux'].append(data['lux'])
    traces['dist'].append(data['dist'])
    render(traces).save('current.png')
```

## Core concepts <a id="core-concepts"></a>

### Concept 1 — The Arduino serial protocol

Arduino doesn't have a "protocol" — it has a USB-to-serial adapter chip that exposes whatever bytes your sketch writes. The community convention is **one packet per line**, `key:value`-separated, newline-terminated:

`pot:512 lux:80 dist:130\n`

The Arduino sketch:

<CodeBlock lang="cpp" file="sketch.ino">
```cpp
void setup() {
    Serial.begin(9600);
}
void loop() {
    int pot = analogRead(A0);
    int lux = analogRead(A1);
    long dist = readUltrasonic(2, 3);   // trigger pin 2, echo pin 3
    Serial.print("pot:"); Serial.print(pot);
    Serial.print(" lux:"); Serial.print(lux);
    Serial.print(" dist:"); Serial.println(dist);
    delay(16);                          // ~60 Hz
}
```
</CodeBlock>

The Python side reads with `pyserial.Serial('/dev/ttyACM0', 9600)`. On macOS and Linux the port is `/dev/cu.usbmodem*`; on Windows it's `COM3` or `COM4`. `9600` is the canonical Arduino baud rate (115200 also common). Both ends must agree on the rate.

### Concept 2 — Parsing the packet

Python parses the line with one comprehension:

<CodeBlock lang="python" file="parse.py">
```python
def parse(line):
    parts = line.strip().split()
    return {p.split(':')[0]: int(p.split(':')[1]) for p in parts}
```
</CodeBlock>

`split()` (no argument) splits on any whitespace and skips empty strings. Each `key:value` becomes a dictionary entry. The result is a Python dict ready for application code.

For more sophisticated protocols (variable-length packets, floats, binary), use a structured format like JSON Lines (`{"pot": 512, "lux": 80}\n`) or MessagePack. The flat `key:value` form is simplest for prototypes; the structured forms scale to dozens of sensors without breaking.

<Admonition type="dyk" title="Did you know · the Arduino IDE compiles to AVR machine code">
A typical Arduino sketch compiles to a few kilobytes of AVR microcontroller machine code that runs at 16 MHz on an 8-bit CPU. Despite the constraints, the Arduino ecosystem has grown to include 100+ board variants (UNO, Mega, ESP32, RP2040), thousands of libraries, and an estimated 10+ million users globally [1]. The whole "physical computing" curriculum at NYU's ITP — birthplace of most modern interactive-art practice — runs on Arduinos [2].
</Admonition>

### Concept 3 — Rolling history and oscilloscope traces

For visualization you typically want a **rolling window** of the last N samples per sensor. The simplest data structure: a Python list that you append to and slice:

<CodeBlock lang="python" file="rolling.py">
```python
traces = {'pot': [], 'lux': [], 'dist': []}

# Each frame:
data = parse(serial.readline().decode())
for key, val in data.items():
    traces[key].append(val)

# Render only the last TRACE_LEN samples
plot(traces['pot'][-TRACE_LEN:])
```
</CodeBlock>

For high-frequency data (>1 kHz), replace the list with a fixed-size `collections.deque(maxlen=N)` — automatically rolls without manual slicing and is O(1) per append.

<Admonition type="important">
A common gotcha: `serial.readline()` **blocks** until a newline arrives. If your Arduino crashes or the cable is unplugged, your Python script freezes. Always wrap the read in a try/except for `serial.SerialException`, set a timeout (`Serial(port, baud, timeout=0.1)`), or use a background thread to keep the main loop responsive.
</Admonition>

**Reflection questions**

- The photoresistor trace dips every 30 frames. What physical event does that simulate?
- The packet format is `key:value` separated by spaces. What happens if a value contains a space?
- Why is `9600 baud` the default Arduino rate?

<Dropdown summary="Answers">

**Photoresistor dips** — simulates the sensor being briefly covered (a finger over the sensor, a hand passing the lamp). In a real installation, this is the trigger for "user interaction detected."

**Spaces in values** — the parser breaks. For values that might contain spaces (a string sensor name, GPS coordinates), use a more structured format: JSON Lines, or quote the values, or pick a different separator.

**9600 baud** — historical default, reliable across all Arduino boards and USB-serial adapters. 115200 is faster (12× more samples/sec) but used to be unreliable on long cables. Modern hardware handles 115200 fine; new sketches often use it.

</Dropdown>

</Exercise>

def hsv_to_rgb(h, s, v):
    # quick HSV (0..360, 0..1, 0..1) to RGB (0..255)
    h = h / 60
    c = v * s
    x = c * (1 - abs((h % 2) - 1))
    if h < 1:   r, g, b = c, x, 0
    elif h < 2: r, g, b = x, c, 0
    elif h < 3: r, g, b = 0, c, x
    elif h < 4: r, g, b = 0, x, c
    elif h < 5: r, g, b = x, 0, c
    else:       r, g, b = c, 0, x
    m = v - c
    return (int((r + m) * 255), int((g + m) * 255), int((b + m) * 255))

hue = data['pot'] / 1023 * 360
brightness = data['lux'] / 1023

color = hsv_to_rgb(hue, 1.0, brightness)
draw.ellipse([x - 60, size[1]//2 - 60, x + 60, size[1]//2 + 60], fill=color)

#### Make it your own

- **Multiple Arduinos.** Open multiple `Serial` ports, one per device. Each can drive a different visual element of a single installation.
- **Bidirectional.** Write to the Arduino (with `ser.write(b'led:on\n')`) to control LEDs, motors, or servos from Python.
- **Wireless.** Replace USB serial with WiFi or Bluetooth via ESP32 / Raspberry Pi Pico W. The protocol stays the same; the transport changes.

</Exercise>

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

Arduino reads sensor voltages, writes them as newline-terminated `key:value` packets over USB serial. Python reads with `pyserial`, parses with a dict comprehension, drives whatever visualization you want. The Arduino sketch is half a dozen lines; the Python side is the only sophisticated part. Rolling history buffers + per-sensor traces give an oscilloscope-style dashboard. Same pattern with `pyserial.Serial('/dev/ttyACM0')` instead of synthetic packets, and the visualization runs on real hardware.

</Admonition>

**Common pitfalls to avoid**

- **Blocking `readline`.** Wrap in a timeout or thread; otherwise your script freezes on disconnect.
- **Baud-rate mismatch.** Both ends must agree (9600, 115200, etc.). Symptom: garbled bytes that decode as Unicode errors.
- **Packets that contain spaces in values.** The flat `key:value` format breaks. Use JSON Lines or quote values.
- **Forgetting newline-termination.** Without `\n`, `readline` waits forever for the end of the packet.
