## Overview <a id="overview"></a>

Frame differencing (11.1.1) compares consecutive frames and calls anything different "motion." It works on a closed studio shot — but fires false positives on every lighting flicker, every camera shake, every passing cloud. **Background subtraction** is the production-grade alternative: build a model of "what the static scene looks like," subtract it from each new frame, and call the remainder motion.

The cheapest background model is a **running average** — a per-pixel exponential filter that slowly tracks the static scene. Stuff that stays put gets absorbed into the background; stuff that moves doesn't. The result tolerates slow lighting changes (sunrise, fluorescent flicker) while still firing on people walking through frame. This pattern has driven every consumer surveillance camera since the mid-1990s [1], and the underlying technique scales up to OpenCV's MOG2 and KNN background subtractors used in production CV systems.

### Learning objectives

<ol class="obj-list">
  <li>Build a running-average background model with a per-pixel exponential update.</li>
  <li>Update the background only on **still** pixels — never on the moving subject — so the model doesn't absorb the moving object.</li>
  <li>Apply a binary threshold to the background-subtracted frame to produce a motion mask.</li>
  <li>Recognise this as the entry point to the OpenCV background-subtractor family (MOG2, KNN, GSOC) used in production CV.</li>
</ol>

## Quick start — running-average background <a id="quick-start"></a>

<CodeBlock lang="python" file="quick_start.py">
```python
import numpy as np

bg = None
alpha = 0.05  # background-update rate; smaller = slower adaptation

for frame in stream:
    gray = to_gray(frame).astype(np.float32)
    if bg is None:
        bg = gray.copy()
        continue

    diff = np.abs(gray - bg)
    motion_mask = (diff > 22).astype(np.uint8) * 255

    # Update background only on still pixels (where mask is 0)
    still = motion_mask == 0
    bg[still] = (1 - alpha) * bg[still] + alpha * gray[still]

    yield render_with_overlay(frame, motion_mask)
```
</CodeBlock>

<Admonition type="tip">
The key insight: the background model **shouldn't include the moving subject**. If you naively run-average every frame, the subject's silhouette slowly bleeds into the background, and after 10 seconds your model "knows" about a person who has actually moved away. Updating only on still pixels (where `motion_mask == 0`) prevents this absorption.
</Admonition>

## Core concepts <a id="core-concepts"></a>

### Concept 1 — Per-pixel running average

A running average is an exponentially-weighted update:

`bg(t+1) = (1 - alpha) * bg(t) + alpha * new_observation`

`alpha` is the **update rate**: 0 means never adapt (frozen reference frame); 1 means snap to the latest frame (no memory, equivalent to consecutive-frame differencing). Typical values 0.01–0.1.

The model is **per-pixel** — each pixel maintains its own running average. NumPy makes this one line: `bg = (1 - alpha) * bg + alpha * gray`. No loops.

### Concept 2 — Selective background update

If you update the background on *every* pixel of *every* frame, including pixels currently showing the moving subject, the subject's pixel values get blended into the background. After enough frames, the background "remembers" the subject — and when the subject moves away, the model treats the empty space as "motion" (a ghost).

The fix: update the background **only where the motion mask is zero** — only on pixels currently classified as still:

<CodeBlock lang="python" file="selective_update.py">
```python
still = motion_mask == 0
bg[still] = (1 - alpha) * bg[still] + alpha * gray[still]
```
</CodeBlock>

Pixels under the moving subject keep their old background value; pixels showing the static scene get updated. When the subject moves away, the previously-occluded background pixels start updating again and re-converge to the actual scene.

<Admonition type="dyk" title="Did you know · MOG2 is a learned per-pixel mixture model">
OpenCV's `cv2.createBackgroundSubtractorMOG2()` upgrades the running-average idea with a **Mixture of Gaussians** model per pixel: each pixel maintains 3–5 Gaussians representing modal brightness values [2]. Trees swaying in wind have two modes (leaf-blocked vs sky-visible); MOG2 handles them; a single running average can't. The KNN variant uses a non-parametric clustering instead. Both are drop-in replacements for the running-average code here, with 1–2 lines of OpenCV API.
</Admonition>

### Concept 3 — Threshold, morphology, post-processing

The raw `diff > 22` motion mask is noisy: small sensor noise puts isolated pixels above threshold. Production pipelines clean the mask with **morphological operations**:

- **Erosion** — shrink each "motion" region by 1–2 pixels. Removes isolated noise blobs.
- **Dilation** — grow each region back by 1–2 pixels. Reconnects fragmented motion regions.
- **Open** (erode then dilate) — removes noise while preserving large blobs.
- **Close** (dilate then erode) — fills small holes in the mask.

In OpenCV: `mask = cv2.morphologyEx(mask, cv2.MORPH_OPEN, kernel)`. The result is a clean binary mask suitable for downstream processing — blob tracking (11.2.2), object counting, or rendering an overlay.

<Admonition type="important">
The motion mask is the **intermediate product**; what you actually do with it is application-specific. Render an overlay (this lesson), find connected components (11.2.2 blob tracking), count motion events, or trigger an alert. The background subtractor is the front-end; the downstream module is what decides what "motion" means in your domain.
</Admonition>

**Reflection questions**

- The first 10 frames show no figure. What is the background model doing in those frames?
- What happens to the background after the figure walks across the scene?
- What value of `alpha` would cause the figure to be absorbed into the background?

<Dropdown summary="Answers">

**Initialisation** — the first 10 frames have no motion, so every pixel is "still" and the background converges to the empty scene. After 10 frames the model is well-tuned; from then on, motion mask correctly fires only on the walker.

**After walk-through** — the background is unchanged. The walker's pixel positions were always "moving" while the walker was there, so the background never updated under the walker. As the walker moves, previously-occluded pixels become "still" again and get re-included in the background.

**Absorption threshold** — if the background updated *under* the walker (no selective update), or if `alpha` were extremely high (say 0.5), the walker would partially blend into the background within seconds and the detector would fail. The selective-update step is what keeps the model robust.

</Dropdown>

</Exercise>

<Exercise n={2} kicker="MODIFY" title="Tune the background parameters">

**Goals**

1. **Slower update.** Drop `alpha` from 0.05 to 0.005. The background adapts very slowly; sudden lighting changes will produce spurious motion.
2. **Higher threshold.** Raise the diff threshold from 22 to 50. Only larger pixel changes count as motion; the walker shows up more weakly.
3. **No selective update.** Remove the `still` mask and update the background unconditionally. Watch the walker get absorbed.

<Dropdown summary="Goal 1 — what to expect">

Slow-changing scenes look the same. Fast lighting changes (a cloud passing, fluorescent flicker) trigger false-positive motion. Useful only for very controlled environments.

</Dropdown>

<Dropdown summary="Goal 2 — what to expect">

The walker is partially detected — only the high-contrast edges of the figure trigger. Used when you specifically want to ignore weak motion (e.g. small animals, distant traffic).

</Dropdown>

<Dropdown summary="Goal 3 — what to expect">

The walker leaves a "ghost trail" — pixels they recently occupied get registered as motion *after* they move away, because the background absorbed the walker and now sees the original wall as "different." Demonstrates exactly why selective update matters.

</Dropdown>

</Exercise>

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

Frame differencing is the cheapest motion detector but fires on every flicker. The running-average background model tolerates slow lighting drift. Updating the background only on pixels currently classified as still prevents the moving subject from being absorbed into the model. Morphological open/close cleans the binary mask. This is the entry point to OpenCV's MOG2 and KNN background subtractors used in production CV. Next lesson swaps the mask for connected-component analysis to identify and track individual motion blobs.

</Admonition>

**Common pitfalls to avoid**

- **Unconditional background update.** The moving subject gets absorbed; you see ghost trails.
- **Threshold too low.** Every flicker registers as motion. Threshold too high: legitimate motion is missed.
- **No morphology.** Per-pixel noise drives false-positive detections. Always erode-then-dilate.
- **Frozen background.** `alpha = 0` works only in fully-controlled environments; real scenes drift.
