## Overview <a id="overview"></a>

The shadow lesson composited two layers with a boolean mask — a binary choice per pixel. **Blend modes** generalise that decision to a *continuous* formula: each output pixel is some function `f(A, B)` of the same pixel in the two input layers, computed in normalised `[0, 1]` space. Multiply darkens, screen lightens, overlay does both, difference highlights changes. The Porter–Duff alpha-compositing paper of 1984 is the canonical reference, but every image editor since has added a small zoo of additional modes that all reduce to the same pattern: convert to float in `[0, 1]`, apply the formula, clip, convert back to `uint8` [1, 2]. This lesson implements the five canonical modes from scratch and lays them out in a comparison grid.

### Learning objectives

<ol class="obj-list">
  <li>Normalise `uint8` images to float `[0, 1]` and back; explain why blend formulas live in that space.</li>
  <li>Implement `multiply`, `screen`, `overlay`, `difference`, and `add` blend modes as one-line NumPy expressions.</li>
  <li>Predict the output of a blend mode from a sketch of its formula (multiply → dark, screen → light, overlay → S-curve, difference → edges).</li>
  <li>Lay out a 1-row 5-panel grid that compares blend modes side-by-side using `np.hstack`.</li>
</ol>

## Quick start — multiply two coloured gradients <a id="quick-start"></a>

<CodeBlock lang="python" file="quick_start.py">
```python
import numpy as np
from PIL import Image

size = 400

# Two coloured gradients for the demo
y, x = np.mgrid[:size, :size] / size
A = np.zeros((size, size, 3), dtype=np.float64)
A[..., 0] = x            # red ramps left → right
A[..., 1] = y            # green ramps top → bottom
A[..., 2] = 0.3

B = np.zeros((size, size, 3), dtype=np.float64)
B[..., 0] = 0.5
B[..., 1] = 1 - x        # green ramps right → left
B[..., 2] = 1 - y        # blue ramps bottom → top

# Multiply blend: per-channel, in [0, 1] space
multiplied = A * B

out = (multiplied * 255).astype(np.uint8)
Image.fromarray(out).save('multiply_demo.png')
```
</CodeBlock>

The whole blend operation is one expression: `A * B`. The rest of the script is normalisation in (`/ 255`) and out (`* 255`). Every other blend mode in this lesson is the same shape — one NumPy expression per mode.

## Core concepts <a id="core-concepts"></a>

### Concept 1 — Normalise to `[0, 1]` and clip back

Blend mode formulas are defined on values in `[0, 1]`, not `[0, 255]`. Two reasons:

- Multiplying `uint8` values overflows at `256`; in float `[0, 1]` the product is always in range.
- The formulas come from compositing literature where colours are fractions of full intensity, not integer counts.

The pipeline is always the same:

```python
A_f = A_uint8.astype(np.float64) / 255
B_f = B_uint8.astype(np.float64) / 255

result_f = some_blend(A_f, B_f)           # produces values in [0, 1]

result = np.clip(result_f * 255, 0, 255).astype(np.uint8)
```

Skipping the clip is the most common subtle bug — *some* blend formulas (add, screen with bright inputs) overshoot `1.0` even with valid inputs.

<Admonition type="important">
Blend modes operate **per channel**. R blends with R, G with G, B with B. None of the modes in this lesson cross channels — the output's red is a function of the inputs' reds only. That is what lets you write `A * B` for an entire RGB image and have it just work.
</Admonition>

### Concept 2 — The five canonical modes

Five formulas cover most of what photo editors expose [3].

```python
def multiply (A, B): return A * B
def screen   (A, B): return 1 - (1 - A) * (1 - B)
def add      (A, B): return A + B                       # caller must clip
def difference (A, B): return np.abs(A - B)
def overlay  (A, B):
    return np.where(A < 0.5,
                    2 * A * B,
                    1 - 2 * (1 - A) * (1 - B))
```

What each one *does*, intuitively:

- **Multiply** — output is darker than either input. Black times anything is black; white times anything is the other input.
- **Screen** — the inverse-multiply. Output is lighter than either input. White screened with anything is white; black screened is the other input.
- **Add** — straight sum, then clip. Saturates fast; useful for additive lighting.
- **Difference** — absolute difference. Same pixel in both layers → black; very different → bright.
- **Overlay** — multiply where the *base* is dark, screen where the base is light. Contrast booster.

<Admonition type="dyk" title="Technical note · why overlay needs `np.where`">
Overlay is the only mode in this group that *branches* per pixel. It is multiply where the base is dark and screen where the base is light. The two regimes ensure the output stays in `[0, 1]` no matter where on the curve a pixel sits, but the branching means a scalar formula won't do — you need `np.where` (or `np.select` for more cases) to dispatch [4].
</Admonition>

### Concept 3 — Pair sketches and predictable outcomes

You can predict a blend mode's output by mental arithmetic on a handful of extreme cases. Multiply applied to white-on-anything returns the other image; difference applied to identical layers returns black; add applied to two greys gives near-white.

| Mode | `A=0` | `A=0.5` | `A=1` |
|------|------|---------|------|
| Multiply  | `0`              | `0.5 B` | `B` |
| Screen    | `B`              | `0.5 + 0.5 B` | `1` |
| Add       | `B` (clip 1) | `0.5 + B` (clip 1) | `1` |
| Difference| `B`              | `\|0.5 − B\|` | `1 − B` |
| Overlay   | `0`              | `B`     | `1` |

Reading the columns: when `A = 0`, multiply zeroes everything; screen and add return the underlying `B`; overlay zeroes (multiply branch); difference returns `B`. The same table is what artists internalise to pick a mode by intent: "make this layer act as light" → screen or add; "make it act as ink" → multiply.

<Exercise n={1} kicker="EXECUTE" title="Run the multiply blend">

Run `multiply_demo.py` from the downloads. Look at the output, then mentally trace where each colour came from.

**Reflection questions**

- Why is the top-left corner of the output close to black?
- The bottom-right corner has full green and full blue contributions from B, but full red from A. What colour does it produce?
- What blend formula would make the *top-left* corner bright instead of dark?

<Dropdown summary="Answers">

**Black top-left** — at `(x, y) ≈ (0, 0)`: A is `(0, 0, 0.3)` (almost black) and B is `(0.5, 1, 1)`. The element-wise product is `(0, 0, 0.3)`. Black times anything stays black.

**Bottom-right colour** — at `(x, y) ≈ (1, 1)`: A is `(1, 1, 0.3)` and B is `(0.5, 0, 0)`. Product is `(0.5, 0, 0)` — a dim red. Multiply collapses any channel where *either* input is low.

**Light top-left** — `screen(A, B) = 1 - (1 - A) * (1 - B)`. Where A is dark, `(1 - A)` is near 1, and the product `(1-A)(1-B)` stays small only if B is also light — meaning screen *lifts* dark regions when paired with a light B.

</Dropdown>

</Exercise>

<Dropdown summary="Complete solution">

<CodeBlock lang="python" file="exercise3_solution.py">
```python
import numpy as np
from PIL import Image

SIZE = 200
GUTTER = 6

def two_gradients(size):
    y, x = np.mgrid[:size, :size] / size
    A = np.stack([x, y, np.full_like(x, 0.3)], axis=-1)
    B = np.stack([np.full_like(x, 0.5), 1 - x, 1 - y], axis=-1)
    return A, B

def multiply  (A, B): return A * B
def screen    (A, B): return 1 - (1 - A) * (1 - B)
def overlay   (A, B): return np.where(A < 0.5, 2 * A * B, 1 - 2 * (1 - A) * (1 - B))
def difference(A, B): return np.abs(A - B)
def add       (A, B): return A + B

A, B = two_gradients(SIZE)
panels = [multiply(A, B), screen(A, B), overlay(A, B), difference(A, B), add(A, B)]

gutter = np.zeros((SIZE, GUTTER, 3), dtype=np.float64)
pieces = []
for i, panel in enumerate(panels):
    pieces.append(panel)
    if i < len(panels) - 1:
        pieces.append(gutter)
grid = np.hstack(pieces)

out = (np.clip(grid, 0, 1) * 255).astype(np.uint8)
Image.fromarray(out).save('blend_grid.png')
```
</CodeBlock>

**How it works:**

- Each blend function is a one-line NumPy expression on the float-normalised inputs.
- `np.hstack` is the simplest "lay panels horizontally" call there is; the gutters are thin black panels between the content panels.
- The final clip on `[0, 1]` protects against the `add` mode overshooting.

</Dropdown>

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

A blend mode is a pixel-wise function `f(A, B)` defined on float values in `[0, 1]`. The standard pipeline is normalise (`/ 255`), apply the formula, clip to `[0, 1]`, denormalise (`* 255`). Five formulas cover the bulk of what artists use: multiply (darken via per-channel product), screen (lighten via inverse multiply), overlay (contrast via piecewise multiply/screen), difference (highlight divergence via absolute subtract), and add (straight sum with clip). All five operate per channel — no cross-channel logic — which means the same one-line expression applies to grayscale or RGB without change. The same idea generalises into the dozen-plus modes shipping in modern editors; once you understand multiply and screen, the rest of the family is variations on those two themes.

</Admonition>

**Common pitfalls to avoid**

- Forgetting to normalise — `uint8` multiplication overflows at 256, so `A * B` on raw uint8 produces nonsense.
- Forgetting to clip after `add` — the sum can exceed `1.0` and `(arr * 255).astype(uint8)` wraps around to 0.
- Using `np.where` with arrays of different shape — broadcasting works, but a 2D mask on a 3D image needs `mask[..., None]` to broadcast cleanly.
- Implementing overlay without the `np.where` branch — a single formula cannot produce both the multiply and screen regimes.
- Confusing multiply with element-wise *and* operations — `A & B` is bitwise on integers and undefined on float arrays.
