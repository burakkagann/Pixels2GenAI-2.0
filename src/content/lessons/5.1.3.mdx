## Overview <a id="overview"></a>

A firework is two particle systems chained together. The first is one rocket — a single fast-moving particle that rises against gravity, decelerates, and reaches an apex. The second is the burst — dozens of sparks spawned at the rocket's peak, each one given a random direction and falling under its own copy of gravity. The interesting part is the *transition*: at the moment the rocket's vertical velocity flips from negative (rising) to positive (falling), it spawns its sparks and disappears. That one-line state change is what makes the system look like a firework rather than two unrelated animations.

### Learning objectives

<ol class="obj-list">
  <li>Chain two particle systems with a state-transition event — apex detection by sign-flip on vertical velocity.</li>
  <li>Apply gravity uniformly to a population (constant addition to `vy` each frame).</li>
  <li>Use a per-particle `life` counter to fade and retire sparks without ballooning memory.</li>
  <li>Compose colour fade with canvas-fade for two overlapping kinds of motion blur.</li>
</ol>

## Quick start — one rocket, one burst <a id="quick-start"></a>

A rocket is just a particle whose state changes at its apex. The apex is when `vy >= 0` for the first time after launch — the moment gravity has cancelled out the launch velocity.

<CodeBlock lang="python" file="quick_start.py">
```python
class Rocket:
    def step(self):
        self.vy += GRAVITY
        self.y += self.vy
        if self.vy > -0.5 and not self.exploded:
            self.exploded = True   # next frame, spawn sparks and retire
```
</CodeBlock>

<Figure

<Admonition type="tip">
The `> -0.5` threshold catches the apex one frame *before* the rocket is perfectly stationary. Without that small buffer the rocket would explode mid-fall, after gravity had already pulled it slightly downward — visually noticeable as a "delayed" burst.
</Admonition>

## Core concepts <a id="core-concepts"></a>

### Concept 1 — Apex detection by velocity sign-flip

Detecting when a projectile reaches its maximum height does not require maximising a function. The apex is uniquely defined as the moment the vertical velocity passes through zero. Negative `vy` means rising (in our top-down-y-axis coordinate system); positive `vy` means falling.

<CodeBlock lang="python" file="apex_demo.py">
```python
self.vy += GRAVITY          # gravity (positive — y increases downward)
self.y += self.vy
if self.vy > -0.5 and not self.exploded:
    self.exploded = True    # triggers the burst on the next loop iteration
```
</CodeBlock>

This is also how ballistics tracking works in real life: radar detects the moment a missile's velocity vector starts pointing downward and flags it as having peaked.

<Admonition type="note">
The `not self.exploded` guard is what keeps each rocket from spawning *multiple* bursts. Without it, the moment `vy` passes through zero, every frame thereafter spawns a new burst until the rocket falls offscreen.
</Admonition>

### Concept 2 — Radial burst from a single point

To make a burst, spawn N sparks at the same position, each with a velocity vector pointing in a random direction. The direction is a random angle; the speed is a random magnitude. Converting `(angle, speed)` to `(vx, vy)` is the polar-to-Cartesian formula you have used in every previous shape lesson.

<CodeBlock lang="python" file="spark_demo.py">
```python
angle = random.uniform(0, 2 * math.pi)
speed = random.uniform(0.5, BURST_SPEED)
self.vx = speed * np.cos(angle)
self.vy = speed * np.sin(angle)
```
</CodeBlock>

Uniformly-distributed angles produce a circularly-symmetric burst. If you sample angles from a narrower range (say `[π/3, 2π/3]`), you get a fan. If you sample from a Gaussian centred on one angle, you get a stream.

<Admonition type="important">
Each spark needs **its own** copy of position and velocity. A common bug is sharing one velocity vector across all sparks — they all move identically and the "explosion" looks like a single moving dot.
</Admonition>

### Concept 3 — Lifetimes and colour fade

A naive list of sparks grows without bound — every burst adds 90 entries and they never leave. Two cures, both standard:

1. A per-spark `life` counter that decrements each frame; when it hits zero, the spark is filtered out of the list.
2. Brightness scaling by `life / PARTICLE_LIFE` so each spark fades smoothly as it dies.

<CodeBlock lang="python" file="lifetime_demo.py">
```python
self.life -= 1
fade = max(0.0, s.life / PARTICLE_LIFE)
colour = tuple(int(c * fade) for c in s.colour)
canvas[y, x] = colour
# at the end of each frame:
sparks = [s for s in sparks if s.life > 0 and s.y < HEIGHT]
```
</CodeBlock>

<Admonition type="dyk" title="Did you know? · Disney's particle engine">
Pixar's RenderMan particle engine had a built-in "shutdown function" for particles by the late 1980s — one of the first commercial systems to formalise lifetimes as primary state. The lesson that "every particle eventually dies" is older than the field's biggest hits.
</Admonition>

Three exercises in **Execute → Modify → Create** order.

<Exercise n={1} kicker="EXECUTE" title="Run the firework show">

Download `fireworks.py` and run it. It writes `fireworks.gif` and a mid-show still frame as `fireworks_frame.png`.

<Download href="/lessons/5.1.3/fireworks.py" label="fireworks.py — complete reference implementation" />

**Reflection questions**

- Why do the sparks fall but the rocket also fell — why does the rocket disappear at apex?
- What sets the visual difference between a "tight" burst and a "soft" burst?
- Why does the canvas fade per frame even though particles already have their own brightness fade?

<Dropdown summary="Answers">

**Rocket vs spark fall** — the rocket is removed from `rockets` as soon as `exploded == True`. It never reaches a "falling" frame because the code skips it after one apex detection. The sparks fall freely; the rocket would too if we kept it in the list, but the explosion replaces the single point with a burst.

**Tight vs soft burst** — `BURST_SPEED`. With a higher max speed the sparks travel further before their life runs out, producing a wide, sparse explosion. With a lower max speed the burst stays compact and fades quickly. Try 2.0 (tight) and 7.0 (showy).

**Two fades** — the per-spark brightness fade (`fade = life / LIFE`) is per-particle; it dims each spark as it ages. The canvas fade (`TRAIL_FADE = 0.88`) is global; it leaves a slowly-darkening trail of where the particles *have been*. Both together create the "fluorescent" look of a real firework — bright leading edges with dim memory tails.

</Dropdown>

</Exercise>

<Exercise n={2} kicker="MODIFY" title="Reshape the show">

Edit the CONFIG block at the top of `fireworks.py`.

**Goals**

1. **Slower, lazier**: halve `GRAVITY` to `0.09`. The rockets rise higher and the sparks float down gently.
2. **Bigger bursts**: set `BURST_PARTICLES=250` and `BURST_SPEED=6.5`.
3. **Single colour**: replace `PALETTE` with one entry, e.g. `[(255, 200, 80)]`. Every rocket is gold.
4. **Sky colour**: change `BG` to a deep blue twilight `(20, 25, 50)` and reduce `TRAIL_FADE` to `0.92` for longer trails.

<Dropdown summary="Goal 1 — what to expect">

Halving gravity doubles the rise time. Rockets reach the top of the canvas; their bursts spread further before falling. The whole show feels weightless — more like a slow-motion shot than the snappy real-time original.

</Dropdown>

<Dropdown summary="Goal 2 — what to expect">

Dense bursts. With 250 sparks per rocket and high initial speed the explosion fills a quarter of the canvas. Memory and render time scale linearly with `BURST_PARTICLES * concurrent_bursts`; if frame rate drops, that is why.

</Dropdown>

<Dropdown summary="Goal 3 — what to expect">

Identical structure, monochromatic palette. Useful for grading a single-element scene against a multi-colour reference: the eye picks up motion structure more clearly when colour is held constant.

</Dropdown>

<Dropdown summary="Goal 4 — what to expect">

The longer trails turn the canvas into a streak painting — each burst leaves a glowing memory for several seconds. Combined with twilight blue this reads as "long-exposure photograph of fireworks", which is in fact what the algorithm now imitates.

</Dropdown>

</Exercise>

<Dropdown summary="Hint — random angles uniformly on a circle">

```python
angle = random.uniform(0, 2 * np.pi)
speed = random.uniform(0.5, BURST_SPEED)
self.vx = speed * np.cos(angle)
self.vy = speed * np.sin(angle)
```

Uniformly random angles produce a circularly-symmetric burst. The minimum speed of `0.5` prevents "zero-velocity" sparks that would just sit at the apex.

</Dropdown>

<Dropdown summary="Hint — half gravity">

```python
self.vy += GRAVITY * 0.5
self.x += self.vx
self.y += self.vy
self.life -= 1
```

Sparks feel only half the gravity that rockets do. The choice is aesthetic — real fireworks have sparks that descend slowly because they are lighter than the shell. Try `1.0 * GRAVITY` to see the difference (the burst collapses into a streak).

</Dropdown>

#### Make it your own

- **Coloured trails**: change `PARTICLE_COLOUR` so each spark inherits the rocket's colour with slight variation per spark.
- **Secondary explosions**: when a spark's life hits 30, give it a 5% chance to spawn three smaller sparks. Chain-fireworks.
- **Ringed burst**: sample angles uniformly but speed uniformly in `[5.0, 5.5]` — narrow speed window. The burst becomes a perfect expanding ring rather than a disc.

</Exercise>

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

A firework is a state machine: one rocket, one apex transition, many sparks. The rocket detects apex by watching its own velocity sign; the apex event spawns sparks at the rocket's position with random angles and speeds; each spark lives a finite number of frames and fades as it ages. The pattern — *one master agent spawns many child agents on an event* — is exactly how you would build any "explosion", "shower", or "burst" effect, including blood splatter in games, sparks in welding sims, and pollen dispersion in biological visualisations.

</Admonition>

**Common pitfalls to avoid**

- No `not self.exploded` guard. The rocket explodes on every frame after the apex until it falls off the canvas — sparks for days.
- Sharing one `vx, vy` across all sparks. The "burst" becomes a single moving dot.
- No `life` decrement. Sparks accumulate forever, slowing the simulation.
- Forgetting the brightness fade. Sparks vanish abruptly rather than dimming, which looks like a teleport.
- Spawning a rocket every frame instead of every `ROCKET_INTERVAL`. The sky fills with overlapping bursts and the structure disappears.
