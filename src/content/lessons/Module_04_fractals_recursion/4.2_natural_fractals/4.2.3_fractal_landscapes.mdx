## Overview <a id="overview"></a>

The diamond-square algorithm is what you get when you generalise the 1D midpoint-displacement bolt (4.2.2) to a 2D grid. Loren Carpenter introduced it as "stochastic subdivision" in 1980 while making *Vol Libre*, the first computer-generated landscape sequence ever shown in cinema [1]. Pixar's *Genesis Effect* sequence in *Star Trek II: The Wrath of Khan* used it again in 1982 to terraform a dead planet on screen. Within five years, every flight simulator, every fantasy-era video game, and every "demo scene" production was generating its mountains with some variant of this algorithm.

The recipe is short. Start with a square grid of size $2^n + 1$, seed random heights at the four corners, then alternate two steps until every cell is filled. In the **diamond** step, each square's centre takes the average of its four corner heights plus random jitter. In the **square** step, each diamond's centre takes the average of its four diamond-midpoint neighbours plus jitter. Halve the cell size, shrink the jitter scale by `roughness`, repeat. The output is a heightmap with the same Hurst-exponent self-similarity as fractional Brownian motion — and rendered with a biome palette it instantly reads as mountains, forests, beaches, and water [2].

## Quick start — one fractal heightmap <a id="quick-start"></a>

<CodeBlock lang="python" file="quick_start.py">
```python
import numpy as np
from PIL import Image

N, SIZE, ROUGHNESS = 9, 2 ** 9 + 1, 0.55  # 513x513
rng = np.random.default_rng(1)

h = np.zeros((SIZE, SIZE), dtype=np.float64)
# Seed the four corners
h[0, 0]; h[0, -1] = rng.uniform(-1, 1); rng.uniform(-1, 1)
h[-1, 0] = rng.uniform(-1, 1); h[-1, -1] = rng.uniform(-1, 1)

step, scale = SIZE - 1, 1.0
while step > 1:
    half = step // 2
    # DIAMOND step
    for y in range(half, SIZE - 1, step):
        for x in range(half, SIZE - 1, step):
            avg = (h[y-half, x-half] + h[y-half, x+half]
                   + h[y+half, x-half] + h[y+half, x+half]) / 4
            h[y, x] = avg + rng.uniform(-scale, scale)
    # SQUARE step
    for y in range(0, SIZE, half):
        x_start = 0 if (y // half) % 2 == 1 else half
        for x in range(x_start, SIZE, step):
            neigh = [h[y, x-half] if x-half >= 0 else 0,
                     h[y, x+half] if x+half < SIZE else 0,
                     h[y-half, x] if y-half >= 0 else 0,
                     h[y+half, x] if y+half < SIZE else 0]
            n = sum(1 for v in neigh if v != 0) or 1
            h[y, x] = sum(neigh) / n + rng.uniform(-scale, scale)
    step //= 2; scale *= ROUGHNESS

h = (h - h.min()) / max(h.max() - h.min(), 1e-9)
Image.fromarray((h * 255).astype(np.uint8)).save('simple_heightmap.png')
```
</CodeBlock>

<Admonition type="tip">
The grid dimension **must be $2^n + 1$** for the diamond and square steps to land on integer coordinates at every recursion level. 9 → 513, 8 → 257, 10 → 1025. Other sizes break the alignment and leave seams.

## Core concepts <a id="core-concepts"></a>

### Concept 1 — From midpoint displacement to diamond-square

The 1D lightning bolt subdivides a segment by inserting a midpoint perturbed perpendicular to it. In 2D the analogous operation is to insert a height at the centre of each square. But unlike 1D there is also a second set of midpoints to fill: the four **edge midpoints** of each square. Diamond-square handles both with two alternating steps:

- **Diamond step.** For every square with corners at heights $h_1, h_2, h_3, h_4$, set its centre height to the average of the four corner heights, plus a small random jitter. After this step the grid is at a finer half-cell resolution with the corner and centre points filled in — the heights now sit on a **diamond** lattice.
- **Square step.** For every diamond just placed, fill in its four edge midpoints with the average of the four neighbouring diamond centres + jitter. After this step the grid is filled at the new finer resolution — heights sit on a **square** lattice again.

After both steps, halve the cell size and shrink the jitter scale. Repeat until the cell size is 1.

<Admonition type="dyk" title="Did you know · Vol Libre, 1980">
Loren Carpenter joined Boeing in 1979 to render flight-simulator landscapes. Frustrated by the photographs he was supposed to digitise, he wrote a fractal terrain generator instead, used it to make a 2-minute film called *Vol Libre* (1980), and projected it at SIGGRAPH that summer. Lucasfilm hired him out of the audience that same week; Pixar hired him 5 years later, when the rendering group spun out [1].
</Admonition>

### Concept 2 — Roughness and the Hurst exponent

The `roughness` parameter (also called *persistence* or *H'*) controls how fast the jitter shrinks at every level. Just like the lightning bolt's `decay`, it sets the fractal dimension and the apparent roughness of the result:

- **Small roughness (0.3–0.45).** Fine detail decays fast → smooth, rolling hills with a few large features.
- **Medium roughness (0.5–0.6).** Comparable detail at every scale → realistic mountain terrain. This is the diamond-square sweet spot.
- **Large roughness (0.65–0.8).** Fine detail barely shrinks → chaotic, jagged terrain. Looks dramatic but unnatural.
- **Roughness ≥ 0.85.** Detail dominates at every scale → noise. The macro-shape disappears under high-frequency speckle.

The formal relationship: roughness corresponds to a Hurst exponent $H \approx -\log_2$ of the roughness value. Fractional Brownian motion with Hurst $H$ in the interval $(0, 1)$ has fractal dimension $D = 3 - H$ in 2D, so the same `roughness` knob spans terrain dimensions from $D \approx 2.0$ (smooth) up to $D \approx 2.6$ (rough) [2].

### Concept 3 — Heightmap to biome map

A grayscale heightmap is mathematically complete but visually flat. Partition the height range into bands and assign each band a colour and the same data instantly reads as topography:

<CodeBlock lang="python" file="biomes.py">
```python
def biome_colour(h):
    rgb = np.zeros(h.shape + (3,), dtype=np.uint8)
    rgb[h < 0.32]                        = (18,  48, 100)   # deep water
    rgb[(h >= 0.32) & (h < 0.42)]        = (52, 105, 160)   # shallows
    rgb[(h >= 0.42) & (h < 0.48)]        = (210, 200, 140)  # sand
    rgb[(h >= 0.48) & (h < 0.65)]        = (90, 150, 80)    # grass
    rgb[(h >= 0.65) & (h < 0.78)]        = (50, 95, 55)     # forest
    rgb[(h >= 0.78) & (h < 0.90)]        = (115, 105, 95)   # rock
    rgb[h >= 0.90]                       = (245, 245, 250)  # snow
    return rgb
```
</CodeBlock>

The biome thresholds are arbitrary — change them and you get a desert (drop the green band), a tundra (extend snow downward), or an archipelago (raise the water threshold). The heightmap stays the same; only the colour interpretation changes.

<Admonition type="important">
The diamond-square heightmap is **isotropic** — statistically identical in every direction. Real geological terrain isn't: erosion follows water flow, so valleys have a directional bias. For convincing rivers you need to post-process the heightmap with a separate erosion simulation (5.3 covers similar physics). Diamond-square is the *shape generator*; physics-based erosion is the *finishing pass*.
</Admonition>

**Reflection questions**

- Why does the grid have to be size $2^n + 1$ and not just $2^n$?
- What goes wrong if you forget to shrink `scale` (the jitter budget) between iterations?
- The four corner heights are seeded randomly. What does the terrain look like if you instead seed all four corners with the same height?

<Dropdown summary="Answers">

**$2^n + 1$ vs $2^n$** — each iteration halves the cell size. Starting from edge length $2^n$, halving $n$ times gets you to cell size 1, which is what you want. With $2^n$ columns instead of $2^n + 1$, the halving lands on half-integer coordinates partway through and the algorithm needs to handle off-grid points.

**Not shrinking scale** — every level adds equally large random jitter. The macro-shape is overwhelmed by tiny noise; the heightmap looks like white noise rather than terrain. Shrinking is what produces the multi-scale structure.

**Same-valued corners** — the heightmap becomes a perfectly symmetric "bowl" or "dome" depending on the sign of the initial jitter, with fractal noise added on top. The macro-shape is determined by the corners; without diversity there, you lose the continental scale.

</Dropdown>

</Exercise>

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

The diamond-square algorithm extends 1D midpoint displacement to a 2D heightmap by alternating two interleaved subdivision steps. Grid size must be $2^n + 1$ for the recursion to land on integers; jitter must decay between iterations or all scales become noise. `roughness` is the single tuning knob, and it maps to a Hurst exponent that sets the fractal dimension of the resulting surface — 0.5–0.6 looks like realistic mountain terrain. Biome colouring is a per-pixel mapping from height band to RGB; the heightmap stays the same, only the palette changes. The same fractal-noise primitive scales up to procedural-content generation in 4.2.4 (DLA aggregates), 4.3 (L-systems for vegetation), and Module 6 (Perlin/Worley noise, where the noise field itself is the output).

</Admonition>

**Common pitfalls to avoid**

- **Grid size not $2^n + 1$.** Misaligned subdivisions, visible seams. Stick to 5, 9, 17, 33, 65, 129, 257, 513, 1025.
- **Jitter not decaying.** Every level adds the same noise → white noise everywhere. `scale *= roughness` after each pair of steps.
- **Forgetting to renormalise.** Heights can drift wildly outside $[-1, 1]$ over many iterations. Renormalise to $[0, 1]$ at the end before rendering.
- **`&` vs `and` in masks.** NumPy element-wise boolean ops are `&`, `|`, `~`. Python's `and`/`or` short-circuit and raise on arrays.
- **Wrap-around expectations.** This implementation does **not** make the heightmap tile seamlessly. For tileable terrain, use periodic boundary conditions in the diamond and square steps.
