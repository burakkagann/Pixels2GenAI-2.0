## Overview <a id="overview"></a>

The Eden growth model is the simplest possible model of a growing colony. Murray Eden published it in 1961 to describe bacterial-colony morphology [1]. Start with one occupied cell. At every step, find every empty cell adjacent to an occupied one — call that set the **perimeter** — pick one uniformly at random, and occupy it. Repeat forever. The colony grows into a roughly circular blob with a *fractal-rough* boundary. Eden's process has no inputs other than initial seed and step count; the entire morphology is a consequence of one rule. The model is the baseline against which every later morphogenesis model in this lesson (differential growth, space colonisation, Turing patterns) is compared.

### Learning objectives

<ol class="obj-list">
  <li>Represent a growing colony as a boolean grid + a perimeter list of candidate cells.</li>
  <li>Implement uniform random sampling from a dynamically-growing list with O(1) removal.</li>
  <li>Recognise the Eden boundary as a fractal — Kardar-Parisi-Zhang universality class — though it visually looks like a disc.</li>
  <li>Use cell age (frame-of-occupation) as a colour channel to visualise growth-front evolution.</li>
</ol>

## Quick start — one cell, one step <a id="quick-start"></a>

<CodeBlock lang="python" file="quick_start.py">
```python
def grow_one(grid, ages, perimeter, age, rng):
    idx = rng.integers(0, len(perimeter))
    r, c = perimeter[idx]
    perimeter[idx] = perimeter[-1]      # swap-remove (O(1))
    perimeter.pop()
    grid[r, c] = True
    ages[r, c] = age
    for nr, nc in [(r-1, c), (r+1, c), (r, c-1), (r, c+1)]:
        if 0 <= nr < GRID and 0 <= nc < GRID and not grid[nr, nc]:
            perimeter.append((nr, nc))
```
</CodeBlock>

## Core concepts <a id="core-concepts"></a>

### Concept 1 — Boolean grid + perimeter list

Two data structures keep growth O(1) per step:

- **Boolean grid** — `grid[r, c]` is `True` if the cell is occupied. Constant-time occupancy lookup.
- **Perimeter list** — explicit list of `(r, c)` tuples that are currently candidates for growth. Constant-time random sampling.

<CodeBlock lang="python" file="data_structures.py">
```python
grid = np.zeros((GRID, GRID), dtype=bool)
ages = np.zeros((GRID, GRID), dtype=np.int32)
perimeter = [(r-1, c), (r+1, c), (r, c-1), (r, c+1)]   # initial neighbours
```
</CodeBlock>

The naive alternative — scan the whole grid each step to find perimeter cells — is `O(N²)` per step and dies past a thousand cells. The list-based version is `O(1)` average per step and scales to millions.

<Admonition type="dyk" title="Did you know? · Same trick in diffusion-limited aggregation">
The "explicit perimeter list" pattern shows up in DLA (lesson 4.2.4), in surface erosion (lesson 6.2.2), and in raster flood-fills used by every paint program. Whenever your simulation has "active cells on a static grid", an explicit list of those active cells is almost always the right data structure.
</Admonition>

### Concept 2 — Swap-remove for O(1) deletion

The naive way to remove `perimeter[idx]` is `perimeter.pop(idx)` — but that shifts every later element forward, an O(n) operation. The trick: copy the last element into the position you want to delete, then `pop()` the (now-duplicated) last element. The order of `perimeter` is now scrambled, but you do not care — you only ever sample uniformly at random from it.

<CodeBlock lang="python" file="swap_remove_demo.py">
```python
idx = rng.integers(0, len(perimeter))
perimeter[idx] = perimeter[-1]    # swap (overwrites idx)
perimeter.pop()                    # remove last
```
</CodeBlock>

This trick is folk knowledge in competitive programming and game-AI agent management. Every time you write `list.pop(arbitrary_index)`, ask whether you actually need order preserved. Almost always you do not.

<Admonition type="important">
The same perimeter cell can appear multiple times in the list if it is adjacent to multiple occupied cells. That is fine — the sampling probability becomes proportional to the number of occupied neighbours, which is in fact the *correct* Eden weighting. Pure-uniform-per-cell would be a different model.
</Admonition>

### Concept 3 — Rough boundaries and KPZ scaling

The Eden boundary is not smooth and never becomes smooth. The roughness — the standard deviation of the boundary's distance from the centre — grows as `t^(1/3)` (in 2D) where `t` is the number of cells added [2]. This places Eden growth in the **Kardar-Parisi-Zhang universality class**: a deep result connecting Eden colonies, ballistic deposition, polymer-chain growth, traffic models, and several models in physics.

Visually: the boundary roughness is what gives the Eden cluster its "biological" rather than "geometric" look. A perfect circle reads as a clock face; an Eden disc reads as a colony of *something alive*.

<Admonition type="note">
The KPZ result is not just about Eden — it is about a whole family of stochastic growth processes. The universality means that growth experiments on cells, slime moulds, paper combustion, and crystal facets all follow the same `t^(1/3)` scaling, regardless of the microscopic rules.
</Admonition>

**Reflection questions**

- Stare at the boundary in the final frame. Does it look "rough enough" to be biological?
- What would change if you removed the `ages` colour channel and just rendered occupied = white?
- Why does growth slow down over time even though the per-step cost is constant?

<Dropdown summary="Answers">

**Biological roughness** — Eden growth captures the right *qualitative* feel of bacterial colonies and tumour edges. Quantitatively the roughness exponent matches some classes of cell growth but differs from others (notably ones with significant cell motility). The takeaway is that even the cheapest rule produces "biology-shaped" structures.

**Without age colouring** — without colour, you cannot see *when* each cell was occupied, so the growth history is invisible. The colour gradient is what reveals that the centre was occupied first and the boundary last, and it makes the simulation a richer pedagogical artefact.

**Slowing growth** — total growth is `total cells / step count`, which is constant at one cell per step. What slows down *visually* is the *radial growth rate*. A circle of radius `r` has perimeter `2πr`, so as the colony grows, more steps are needed to add a uniform ring. Radius grows as `√t`.

</Dropdown>

</Exercise>

<Exercise n={2} kicker="MODIFY" title="Reshape the growth">

**Goals**

1. **Two seeds**: start with two occupied cells far apart. The colonies grow until they collide.
2. **Anisotropic growth**: bias the perimeter sampling so up/down neighbours are 3× more likely than left/right. Watch the colony stretch vertically.
3. **8-connected neighbours**: include diagonals in the neighbour set. Boundary becomes visibly smoother.
4. **Hollow seed**: occupy a ring of 30 cells as the initial state. The interior fills in over time.

<Dropdown summary="Goal 1 — what to expect">

Two roughly circular colonies expand outward. When they meet, the perimeter list for each loses candidates on the side facing the other, and the colonies "freeze" along their contact line. The merged shape is a peanut.

</Dropdown>

<Dropdown summary="Goal 2 — what to expect">

Implement by weighted random choice in the neighbour-append step: append vertical neighbours 3× as often as horizontal. The colony elongates vertically — a textbook example of anisotropy in growth models. Real biofilm experiments produce similar shapes under gradients.

</Dropdown>

<Dropdown summary="Goal 3 — what to expect">

Allowing diagonals lets the colony "fill in" corners faster. The boundary roughness exponent stays the same (still KPZ), but the visible shape is rounder. This is the difference between Moore neighbourhood (8-connected) and Von Neumann (4-connected).

</Dropdown>

<Dropdown summary="Goal 4 — what to expect">

The perimeter starts large and the interior empties don't get occupied until the ring has grown inward to fill them. The age colouring reveals that the outermost cells are oldest, opposite of the seed-from-centre version.

</Dropdown>

</Exercise>

<Dropdown summary="Complete solution">

```python
def grow_one(grid, ages, perimeter, age, rng):
    if not perimeter:
        return
    idx = rng.integers(0, len(perimeter))
    r, c = perimeter[idx]
    perimeter[idx] = perimeter[-1]
    perimeter.pop()
    grid[r, c] = True
    ages[r, c] = age
    for nr, nc in [(r-1, c), (r+1, c), (r, c-1), (r, c+1)]:
        if 0 <= nr < GRID and 0 <= nc < GRID and not grid[nr, nc]:
            perimeter.append((nr, nc))
```

</Dropdown>

#### Make it your own

- **Eden-B variant**: sample a *site* uniformly at random from the perimeter instead of a *position*. Boundary becomes smoother but the topology of fluctuations changes.
- **Multi-species**: two colours competing for the same perimeter. Whoever reaches a cell first gets it. Watch one species win or the boundary between them lock.
- **Plot perimeter size over time**. It grows as `√t` for ordinary Eden — visual confirmation of the scaling law.

</Exercise>

## Summary <a id="summary"></a>

<Admonition title="Key takeaways">

Eden growth is the simplest possible morphogenesis model: one occupied seed, repeated uniform sampling of the perimeter, occupy. Two data structures — boolean grid plus explicit perimeter list — give O(1) per step. Swap-remove keeps deletion O(1). The Eden boundary is fractal (KPZ universality class) and visually "biological". The pattern is the baseline against which differential growth (5.4.2), space colonisation (5.4.3), and reaction-diffusion (5.4.4) demonstrate their refinements. Get this primitive right and the whole subtopic clicks into place.

</Admonition>

**Common pitfalls to avoid**

- Using `perimeter.pop(idx)` instead of swap-remove. Growth slows to a crawl past 10⁴ cells.
- Removing duplicates from the perimeter "to be tidy". You break the natural neighbour-count weighting.
- Drawing the colony before colouring it by age. Without age colour the GIF tells you nothing about history.
- Forgetting the bounds check on neighbours. The colony grows into negative coordinates and crashes the indexer.
- Re-scanning the grid each step. The whole point of the perimeter list is to avoid this.
